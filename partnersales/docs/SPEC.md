# PartnerSales — 紹介報酬（3段階リファラル）管理システム 仕様書

> ステータス: **事前準備フェーズ（v0 / 設計 + スキャフォールド + 報酬エンジン）**
> 作成: 2026-06-20 / ブランチ: `partnersales`

## 1. 目的

弊社の各サービスごとに **報酬形態（コミッション）** を定義し、**最大3段目** の紹介者まで
紹介報酬を分配する仕組みを構築する。

- **紹介会社（パートナー）ごと** に、進捗と現在発生している報酬額を把握できる
- 各パートナーに **MLM のようなツリー図** で自分の紹介網を管理できる個別ページを発行する
- **自社管理画面** では全パートナーのツリーが無限に広がる様子を俯瞰し、
  どの紹介者が最も成績が良いか・誰を重点的にサポートすべきかを判断できる

## 2. ドメインモデル（用語）

| 用語 | 英語 | 説明 |
|------|------|------|
| サービス | `Service` | 弊社が販売する商材。サービスごとに報酬プランを持つ |
| 報酬プラン | `RewardPlan` | サービス × 段（tier1/2/3）ごとの報酬率または固定額 |
| パートナー | `Partner` | 紹介会社。`parentId` で紹介ツリーを構成（親 = 紹介元） |
| 成約 | `Deal` | あるパートナー経由で発生した売上。金額・サービス・ステータスを持つ |
| 報酬 | `Commission` | 成約から計算され、ツリーを最大3段上って分配される金額 |

### 2.1 ツリー（アップライン）構造と報酬の起点

**報酬はクライアント（弊社 LET と契約した顧客）を起点に計算する。**
クライアントを底に置き、そのクライアントを紹介したパートナーから上方向へ
最大3段のパートナーに分配する。

```
   A（ルート = 弊社の直接パートナー）
   │ 紹介
   B
   │ 紹介
   C
   │ 紹介
  ［クライアント X が LET と契約］
```

クライアント X（C が紹介）が **100万円** 契約した場合:

| 受領者 | 段 | 根拠 | 例（率） | 金額 |
|--------|----|------|---------|------|
| C | tier1 | X を直接紹介したパートナー | 10% | 100,000円 |
| B | tier2 | C を紹介した1段上 | 3% | 30,000円 |
| A | tier3 | B を紹介した2段上 | 2% | 20,000円 |

> - 「3段」は **クライアント（成約者）の上に3段** のパートナー。**4段目以降には分配しない**。
> - 弊社の直接パートナー（ルート）が紹介した場合は上位が居ないため **tier1 の10%のみ**。
> - 報酬率はサービスごとに設定可能（サンプル値。`data/services.ts` で後から追加・変更できる）。

### 2.2 報酬計算ルール

各サービスの `RewardPlan` は段ごとに以下のいずれかを持つ:

- `type: "percentage"` — 成約金額に対する割合（例: tier1=15%, tier2=5%, tier3=2%）
- `type: "fixed"` — 1成約あたりの固定額（例: tier1=30000円）

報酬額 = `confirmed`/`paid` ステータスの成約のみ確定。`pending` は見込みとして別集計。
**ステータスの遷移（報酬確定タイミング）は運用側で手動設定する。**

```
commission(tier) =
  type === "percentage" ? floor(deal.amount * rate)
                        : fixedAmount
```

端数は **円未満切り捨て**（`Math.floor`）で統一。

**自己成約（`isSelfDeal`）**: パートナー自身が弊社と契約（自分が顧客）した場合は
**tier1（本人）への報酬を出さない**。一方、その人の上位の紹介者（tier2 / tier3）には
通常どおり支払う（上位はパートナーを勧誘した実績に対して報酬を得る）。

### 2.3 ステータス遷移

```
Deal:        pending → confirmed → paid
Commission:  accrued（発生）→ payable（支払可能）→ paid（支払済）
```

## 3. 画面構成

### 3.1 パートナー専用ページ `/me`（パートナーログイン）
- 自分を起点とした **ダウンライン・ツリー図**
- 自分の成約・ダウンライン成約からの **発生報酬合計（確定 / 見込み）**
- 支払い状況（未精算・振込済・下限）・**報酬明細・月次締め**
- 招待コードの表示
- ※ `/partners/[slug]` は **スタッフが任意のパートナーを閲覧**する管理用ビュー（同内容）

### 3.2 自社管理ダッシュボード `/`（スタッフ）
- 全パートナーを含む **無限展開ツリー**（折りたたみ可能）
- **リーダーボード**: 紹介者を「自身＋ダウンライン総売上 / 総報酬 / 直紹介数 / 稼働率」でランキング
- 重点サポート提案: 成長率・休眠・ツリー深度などからサポート優先度を算出
- サービス別・段別の報酬発生額サマリ

### 3.3 サービス / 報酬プラン `/services`（スタッフ）
- サービスごとの tier1/2/3 報酬設定の閲覧

### 3.4 スタッフ管理 `/admin`（スタッフ）
- 成約入力・ステータス変更 / 支払い精算 / パートナー登録（認証情報割り当て）

### 3.5 認証
- パートナー: `/login`（事前発行 ID/PASS）→ `/me`
- スタッフ: `/staff/login`（合言葉）→ ダッシュボード・`/admin`
- middleware + HMAC 署名セッション Cookie でロール分離・ページ保護

## 4. 技術スタック

- Next.js 15 (App Router, **動的レンダリング**) / React 19 / TypeScript strict
- Tailwind CSS（feer デザイントークン: `ink`/`cream`/`brand`/`surface`）
- 報酬・支払い・明細の計算は **純粋関数**（`lib/*.ts`）として実装し vitest でテスト
- データは **seed ↔ Supabase 自動切替**（`lib/db/`）。環境変数未設定なら seed で動作
- 認証は middleware + HMAC セッション。管理書き込みは **サーバアクション + service_role**
- 認証ゲートのため静的エクスポートではなく **動的レンダリング**（Vercel / Node）

## 7. 確定した仕様（2026-06-20）

1. **報酬率** — サービスごとにサンプル値を設定。`data/services.ts` で後から追加・変更可能。
2. **段の定義** — クライアント（成約者）の上に **最大3段**。4段目以降には分配しない。
   弊社の直接パートナー（ルート）が紹介した場合は tier1 の率のみ。
3. **自己成約** — tier1（本人）は出さない。上位の tier2 / tier3 には支払う。
4. **報酬確定タイミング** — 運用側で **手動設定**（`pending → confirmed → paid`）。
5. **Notion 連携** — 紹介者登録時に既存 Notion DB（DB_協業先管理）へ追加。
6. **デプロイ** — Vercel/GitHub 連携が途絶しているため git はターミナル経由で運用。
7. **認証** — 弊社が ID/PASS を **事前発行**（Notion 保管）し、アポ後に
   **スタッフが `/admin` で登録**して割り当てる。パートナーは `/login` でログイン。
   自己登録は廃止（スタッフ主導）。
8. **支払い** — 累計確定報酬の **未精算が ¥50,000 に達するまで支払わない**（繰越）。
   支払いは **弊社からの銀行振込のみ**。紹介者が **都度請求書を発行**
   （請求書受領 `invoiced` → 振込完了 `paid`）。決済連携（Stripe 等）は **不要**。

## 8. 支払いフロー

```
確定報酬が累積 → 未精算 ≥ ¥50,000 → 「請求書発行依頼」
  → 紹介者が請求書発行 → スタッフが受領記録(invoiced)
  → 弊社が銀行振込 → スタッフが振込完了(paid)
未精算 < ¥50,000 の間は繰越（支払わない）
```
