# 統合設計: 評価制度 × sales-cockpit × 財務ダッシュボード

作成: 2026-08-06 ／ ブランチ: `claude/evaluation-finance-dashboard-50w8t9`
ステータス: **ドラフト（要決定3点あり → §7）**

---

## 1. 目的（経営陣の要望）

1. **経営陣**: 財務ダッシュボード（slack-let）のクオリティを上げ、同じUIで社内全体の営業成績・個人別の成績（人事評価の材料）まで見られるようにする
2. **評価制度サイト（let-hyoka）**:
   - 営業職: 個人別に「どれぐらい会社に貢献しているか」をリアルタイム表示
   - マーケ職: 業績連動の前提となる「実際に扱っている売上」と「原価としての広告宣伝費」を可視化
3. **共通ルール**: 集計は会計年度（10/1〜9/30）スコープ。年度をまたぐ通算表記はしない（slack-let側は2026-08-06に対応済み）

## 2. 現状の3システム

| システム | データソース | 技術 | 認証 | 個人の概念 |
|---|---|---|---|---|
| **slack-let**（財務） | MFクラウド会計の仕訳（リアルタイム） | Vercel serverless + HTML | CRON_SECRET（Cookie 30日） | なし（取引先・科目のみ） |
| **sales-cockpit**（営業） | Notion（DB_顧客管理 / 架電記録 / 契約管理DB / IS架電KPI） | Next.js + Vercel | （プロジェクト内設定） | **あり**（IS担当・顧客担当） |
| **let-hyoka**（評価制度） | 静的HTML（マーケ実績表は手動転記の静的値） | 静的HTML + Vercel | クライアントサイドSHA-256 + sessionStorage | あり（松本・松岡など明記） |

## 3. データギャップ（統合の核心課題）

1. **「担当者 → クライアント → MF取引先/補助科目」のマッピングが存在しない**
   - sales-cockpit の Notion顧客DBには担当者がいるが、MFの取引先名・売上補助科目とは名寄せされていない
   - 社名表記ゆれ・酷似（例: ビッグ測量設計/ビック測量の法人重複疑い、`MARKETING_DATA_AUDIT.md` §データ品質）がそのまま個人別集計を壊す
   - → **新Notion DB「担当マッピング」を単一ソースにする**
     - **【2026-08-06 作成済み】** 「担当マッピング（担当者×クライアント×MF取引先）」
       - URL: https://app.notion.com/p/1bf24c541f564a679510de3554dcdceb ／ data_source_id: `0dcce66e-e8ad-4f4e-a2b7-8677139d5439`
       - 親: 株式会社LET公式Notion トップ直下（MF連携設定と同列）
       - 列: クライアント名 / 担当者 / MF取引先名 / MF売上補助科目 / 事業区分 / 契約状況 / 名寄せステータス / 備考
       - 23社（松本11・松岡12）をシード投入済み。MF売掛台帳と名前が一致した6社（セントラルフルーツ・アルファガード・ゼロワットパワー・TECNES・ナワショウ・cantera）はMF取引先名を推定入力し「要確認」、残りは「未名寄せ」
       - 法人重複疑いの2行（ビッグ測量設計/ビック測量）には使用禁止の注記入り
2. **マーケの広告宣伝費のクライアント別割付**
   - MF販管費（広告宣伝費・外注費）のうちクライアント案件連動分を、補助科目 or 取引先経由で担当マッピングに紐付ける必要がある
   - 紐付かない広告費は「共通費」として個人別集計から除外し、除外額を明示する（silent dropしない）
3. **契約金額ベース vs 実仕訳ベースのズレ**
   - 評価サイトの現行実績表は契約金額ベースの推定値（23社中10社のみ確定）
   - リアルタイム化は**MF実仕訳ベース**に寄せる。静的表は「契約ベース参考値」として区別して残す（監査文書の方針と整合）

## 4. アーキテクチャ（推奨案）

```
Notion「担当マッピング」DB（新設・単一ソース）
        │
        ▼
slack-let に読み取り専用 集計API を追加（/api/mf/query の許可リスト思想を踏襲）
  GET /api/eval/contribution?fy=2025&person=<担当者>
    → { 売上(実仕訳・FY), クライアント別内訳, 広告宣伝費(案件連動), 粗利貢献 }
  認証: CRON_SECRET とは別の閲覧専用トークン EVAL_READ_TOKEN（書き込み不可・評価用に限定）
        │
        ├─▶ 財務ダッシュボードUI: 「担当者別実績」ページ（経営陣用・同一page-shell）
        └─▶ let-hyoka 評価ページ: 該当セクションだけ fetch で動的化（静的HTMLは維持）
```

- 集計ロジックは slack-let に集約する（MF接続・PL分類・FYスコープ・売掛台帳が既にあるため）。sales-cockpit や評価サイトへMF接続を複製しない
- sales-cockpit は架電・アポ・パイプラインの担当者別実績を既に持つ → 財務UIからは当面リンク統合とし、コード統合はしない（二重実装回避）

## 5. フェーズ計画

| Phase | 内容 | 前提 |
|---|---|---|
| **1** | Notion「担当マッピング」DB新設・初期データ投入（MF取引先名の名寄せ含む） → slack-let に担当者別集計API + 経営陣用「担当者別実績」ページ | 法人重複疑い（ビッグ測量設計/ビック測量）の解消が先 |
| **2** | let-hyoka マーケ評価ページの実績表をAPI駆動に置換（静的値→リアルタイム）。契約ベース表は参考値として残置 | Phase 1 + EVAL_READ_TOKEN 設計 |
| **3** | 営業職の個人別貢献表示（受注→請求仕訳→入金の実績ベース）。sales-cockpit の架電/アポKPIと併記 | 営業の個人↔取引先マッピング整備 |
| **4** | 人事評価ビュー（部門横断の成績一覧・低パフォーマンス検知）。閲覧は経営陣限定 | §7-1 の決定 |

## 6. セキュリティ・権限（重要）

- 評価サイトの現行認証はクライアントサイドSHA-256で強度が低い。**個人別の実績・評価データをリアルタイム表示するページは、閲覧専用トークン（サーバ側検証）へ格上げしてから載せる**
- 個人別成績の全体一覧は経営陣ページのみ。従業員用 `/demo/*` には出さない（本人分のみ表示するかは §7-1 の決定次第）
- EVAL_READ_TOKEN は読み取り専用・評価系エンドポイント限定。CRON_SECRET（全ページ・cron実行可）を評価サイトに埋め込まない

## 7. 決定が必要な点（役員判断）

**【2026-08-10 決定済み】** 以下4点が決定し、Phase 2 相当（暗号化静的配信方式）を実装済み:

1. **売上の定義** → **MF実仕訳ベース**（契約ベース表は参考値として残置）
2. **人件費の見せ方** → **実額をそのまま表示**（従業員ページ含む）
3. **営業（江原）の立替金** → 精算後のPL科目（旅費交通費等）を取引先=本人で集計。立替金勘定は残高参考表示のみ
4. **配信方式** → let-hyoka へは**ページ別パスワード鍵の AES-GCM 暗号化静的焼き付け**（`scripts/bake-eval-data.mjs`）。経営陣リアルタイム版は slack-let `/api/financial/contribution`
