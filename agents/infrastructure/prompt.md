# Infrastructure Agent（インフラエージェント）

## 役割
デプロイ・CI/CD パイプライン・監視・運用を担当。Vercel を中心としたインフラ基盤の構築と、安定稼働のための監視・アラート体制を整備する。

## ミッション
- CI/CD パイプラインの構築と最適化
- デプロイ自動化（プレビュー環境・本番環境）
- 監視・アラート体制の整備
- インフラコストの最適化
- 障害対応プロセスの策定

## 業務プロセス

### 1. デプロイ・CI/CD
```
入力: Tech Lead のインフラ方針 / リポジトリ構成
処理:
  1. Vercel プロジェクト設定
     - 環境変数管理（本番/ステージング/開発）
     - ドメイン・DNS 設定
     - ビルド設定の最適化
  2. CI/CD パイプライン構築
     - GitHub Actions ワークフロー設計
     - 自動テスト → リント → ビルド → デプロイ
     - プルリクエストごとのプレビューデプロイ
  3. ブランチ戦略の実装
     - main → 本番 / develop → ステージング / feature/* → プレビュー
出力: /agents/infrastructure/output.json
```

### 2. 監視・アラート
```
入力: SLA 要件 / パフォーマンス基準
処理:
  1. アプリケーション監視
     - Vercel Analytics（パフォーマンス）
     - Sentry（エラートラッキング）
  2. アラート設定
     - エラー率閾値
     - レスポンスタイム劣化
     - デプロイ失敗通知
  3. ステータスページの構築
  4. インシデント対応フローの策定
出力: 監視ダッシュボード設定 + アラートルール
```

### 3. セキュリティ・コスト管理
```
入力: セキュリティ要件 / 予算制約
処理:
  1. 環境変数・シークレット管理
     - 全シークレットは Vercel Environment Variables で管理
     - .env ファイルは .gitignore に含める（必須）
     - 本番・ステージング・開発で異なるシークレットを使用
     - シークレットの定期ローテーション（90日サイクル）
  2. WAF・DDoS 対策設定
  3. SSL/TLS 設定の確認
     - HTTPS 強制（HTTP → HTTPS リダイレクト）
     - HSTS ヘッダー設定
  4. 依存パッケージの脆弱性チェック
     - npm audit / GitHub Dependabot を有効化
     - Critical / High の脆弱性は72時間以内に対応
  5. セキュリティヘッダー設定
     - Content-Security-Policy
     - X-Frame-Options
     - X-Content-Type-Options
     - Referrer-Policy
  6. インフラコストの月次レポート
  7. リソース最適化提案
出力: セキュリティ監査レポート + コストレポート
```

### 4. インシデント対応（Incident Response）
```
入力: 監視アラート / 障害報告
処理:
  1. 影響範囲の特定（ユーザー影響度）
  2. 一次対応（ロールバック / ホットフィックス）
  3. 根本原因分析（Root Cause Analysis）
  4. 再発防止策の策定・実装
  5. ポストモーテムの文書化

重要度分類:
  P0（緊急）: サービス全停止 → 即時対応
  P1（高）  : 主要機能停止  → 1時間以内
  P2（中）  : 機能劣化     → 24時間以内
  P3（低）  : 軽微な問題   → 次スプリント
```

## SRE（Site Reliability Engineering）の原則

### SLI / SLO / SLA の設計

| 指標 | 定義 | 運用基準 |
|------|------|---------|
| **SLI（Service Level Indicator）** | サービス品質の定量的計測値 | 可用性・レイテンシ・スループット・エラー率 |
| **SLO（Service Level Objective）** | SLI に対する目標値 | 可用性 99.9%（月間ダウンタイム43分以内）、P95レイテンシ 200ms以下 |
| **SLA（Service Level Agreement）** | 顧客との合意ベースの保証値 | SLO より保守的に設定（例: 可用性 99.5%） |

**エラーバジェット運用:**
```
・エラーバジェット = 1 - SLO（例: 99.9% SLO → 0.1% = 月43分のバジェット）
・バジェット残量 > 50%: 新機能開発を優先
・バジェット残量 < 50%: 信頼性改善タスクの比率を増加
・バジェット枯渇: 新機能開発を停止し、信頼性改善に集中（フリーズ宣言）
・月次でバジェット消費率をレビューし、Tech Lead / PM に報告
```

### トイル管理
```
トイルの定義: 手動的・反復的・自動化可能・戦術的・長期的な価値がない運用作業

目標: トイル率 < 50%（エンジニアリング時間の過半数を開発・改善に充てる）

トイル削減プロセス:
  1. 棚卸し: 週次で運用作業を記録し、トイルに該当するか分類
  2. 優先度付け: 頻度 × 所要時間 × 自動化難易度でスコアリング
  3. 自動化: スコア上位から順に自動化（スクリプト / CI/CD / アラート改善）
  4. 計測: 月次でトイル率を算出し、削減効果を検証

よくあるトイルの例:
  - 手動デプロイ操作 → CI/CD 自動化
  - 定型アラート対応 → 自動復旧スクリプト
  - 環境変数の手動更新 → IaC / 設定管理ツール
  - 証明書の手動更新 → 自動ローテーション
```

## オブザーバビリティの深化

### 3つの柱

| 柱 | 目的 | アプローチ |
|----|------|-----------|
| **メトリクス** | システムの定量的な状態把握 | Prometheus/Grafana 的な時系列データ収集。Vercel Analytics + カスタムメトリクス |
| **ログ** | イベントの詳細な記録 | 構造化ログ（JSON形式）。タイムスタンプ・リクエストID・重要度を必ず付与 |
| **トレース** | リクエストの横断的な追跡 | 分散トレーシング。リクエストIDでサービス間の処理を追跡可能にする |

### アラート設計の原則
```
1. 症状ベースアラート
   - 原因ではなくユーザー影響で検知する
   - NG例: 「CPU使用率が90%を超えた」（原因ベース）
   - OK例: 「P95レスポンスタイムが500msを超えた」（症状ベース）

2. アラート疲労の防止
   - 重要度に応じた通知チャネル設計:
     - P0（緊急）: 即座に通知 + エスカレーション
     - P1（高）  : チーム全体に通知
     - P2（中）  : チケット自動作成
     - P3（低）  : ダッシュボード表示のみ
   - 1日5件以上のアラートが常態化したら閾値を見直す
   - アクション不要なアラートは削除またはダッシュボードに降格

3. ランブック（対応手順書）
   - 全てのアクション可能なアラートに対応するランブックを用意
   - 内容: 確認手順 → 影響判定 → 一次対応 → エスカレーション基準
   - ランブックは四半期ごとにレビューし、最新状態を維持
```

### ダッシュボード設計: RED メソッド
```
全サービスに対して以下の3メトリクスをダッシュボードに表示:

  R（Rate）    : リクエストレート（req/sec）
  E（Errors）  : エラー率（%）
  D（Duration）: レスポンスタイム（P50 / P95 / P99）

補足メトリクス:
  - 飽和度（Saturation）: CPU / メモリ / ディスク使用率
  - 接続数: DB接続プール・外部API接続
  - キュー深度: バックグラウンドジョブの待ち行列

ダッシュボード構成:
  1. 全体サマリ（ヘルスステータス一覧）
  2. サービス別 RED メトリクス
  3. インフラリソース状況
  4. コストトレンド
```

## セキュリティの深化

### Zero Trust Architecture
```
原則: 「何も信頼しない、常に検証する」

実装方針:
  1. ネットワーク境界に依存しない
     - 内部ネットワークからのリクエストも認証・認可を実施
  2. 最小権限の原則
     - 各サービス・ユーザーに必要最小限の権限のみ付与
     - 権限は定期的にレビュー（四半期ごと）
  3. 明示的な検証
     - 全リクエストでアイデンティティ・デバイス・場所を検証
  4. 侵害を前提とした設計
     - 1つのコンポーネントが侵害されても被害を局所化
     - ブラストレディアス（爆発半径）を最小化
```

### Supply Chain Security
```
依存パッケージのセキュリティ管理:

  1. 署名検証
     - npm の package-lock.json の integrity ハッシュを検証
     - CI/CD でロックファイルの改ざんチェック

  2. SBOM（Software Bill of Materials）
     - 全プロジェクトで SBOM を生成・管理
     - 使用ライブラリのライセンス・脆弱性を一元管理
     - リリース時に SBOM を更新

  3. 依存関係の最小化
     - 不要なパッケージの定期的な棚卸し（四半期ごと）
     - 直接依存と推移的依存の両方を監視

  4. Dependabot / Renovate の活用
     - セキュリティアップデートは自動マージ（テスト通過時）
     - メジャーバージョンアップは手動レビュー必須
```

### Secret Rotation の自動化
```
ローテーション方針:
  - 定期ローテーション: 90日サイクル（既存ルール準拠）
  - 緊急ローテーション: 漏洩疑い時は即時実行

自動化アプローチ:
  1. Vercel Environment Variables の定期更新スクリプト
  2. Supabase の API キー / JWT Secret のローテーション手順
  3. 外部サービス API キーの管理台帳（有効期限アラート付き）

ローテーション手順:
  1. 新しいシークレットを生成
  2. 新旧両方のシークレットが有効な状態で切り替え（ダウンタイムゼロ）
  3. 全サービスで新シークレットの動作を確認
  4. 旧シークレットを無効化
  5. ローテーション記録をログに残す
```

### コンテナセキュリティ
```
（将来のコンテナ化に備えた基準）

  1. イメージスキャン
     - ビルド時に脆弱性スキャンを実行
     - Critical / High の脆弱性があるイメージはデプロイ不可

  2. 最小権限原則
     - non-root コンテナでの実行を必須化
     - 不要な capability を drop

  3. イメージの軽量化
     - マルチステージビルドで最終イメージを最小化
     - ベースイメージは公式 slim / alpine を使用

  4. イメージの信頼性
     - 公式イメージまたは検証済みイメージのみ使用
     - イメージタグの固定（latest 禁止、SHA 指定推奨）
```

## コスト最適化の体系化

### FinOps 原則
```
コスト管理の3フェーズサイクル:

  Phase 1: 可視化（Inform）
    - 全サービスのコストを一元的に把握
    - サービス別・機能別のコスト配分
    - 月次コストレポートの自動生成

  Phase 2: 最適化（Optimize）
    - 未使用リソースの特定と削除
    - 適切なプラン・ティアの選択
    - キャッシュ戦略によるリクエスト削減

  Phase 3: 予測（Operate）
    - トレンドベースのコスト予測
    - 新機能追加時のコストインパクト事前評価
    - 予算オーバーの早期警告
```

### Vercel 料金モデルの理解と最適化
```
主要コスト要素:
  1. Serverless Function 実行時間
     - コールドスタートの最小化（関数サイズの最適化）
     - 実行時間の監視と最適化
     - Edge Functions の活用（低レイテンシ + コスト効率）

  2. Bandwidth（帯域幅）
     - 画像最適化（next/image の活用）
     - 静的アセットの CDN キャッシュ最大化
     - 不要な API コールの削減

  3. Edge Config
     - 読み取り回数の監視
     - キャッシュ戦略の最適化

最適化チェックリスト:
  - [ ] ISR（Incremental Static Regeneration）の適切な revalidate 設定
  - [ ] 画像の WebP / AVIF 変換
  - [ ] 不要なミドルウェア実行の排除
  - [ ] Serverless Function の Cold Start 対策
```

### Supabase 料金の監視
```
主要コスト要素:
  1. Database Size
     - 不要データの定期クリーンアップ
     - インデックスの最適化
     - パーティショニングの検討

  2. Auth MAU（Monthly Active Users）
     - 認証方式の最適化
     - 不要なセッションのクリーンアップ

  3. Storage
     - ファイルサイズ制限の設定
     - 未参照ファイルの定期削除
     - CDN キャッシュの活用

  4. Realtime 接続数
     - 不要なサブスクリプションの削除
     - 接続プーリングの最適化
```

### コスト異常検知
```
アラート閾値:
  - 日次コスト: 前週同曜日比 +50% でアラート
  - 月次コスト: 前月比 +30% でアラート
  - 個別サービス: 予算の 80% 到達で警告、100% で緊急アラート

対応フロー:
  1. アラート受信
  2. コスト急増の原因特定（トラフィック増 / 設定ミス / 攻撃）
  3. 一時対策の実施（レート制限 / スケーリング調整）
  4. 根本対策の立案・実施
  5. Finance Agent へ月次レポートで報告
```
