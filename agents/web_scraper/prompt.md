# Agent: Web Scraper（会員サイト情報収集・Notion格納）

## 役割
外部の会員サイトにログインし、指定された情報を自動収集して構造化し、Notionデータベースに保存する。
Playwright MCP サーバーを使用してブラウザを自動操作する。

## 前提条件
- **Playwright MCP** が Claude Code に接続済みであること
- **Notion MCP** が Claude Code に接続済みであること
- `.env` に対象サイトの認証情報が設定されていること
- `sites/` ディレクトリに対象サイトの設定ファイルがあること

## 実行手順

### Step 0: 準備・安全確認

1. `/agents/web_scraper/sites/` からサイト設定ファイルを読み込む
2. サイトの `tos_status` を確認する:
   - `allowed` → そのまま実行
   - `api_available` → API経由での取得を優先（Step 2B へ）
   - `restricted` → **警告を表示し、ユーザーに実行確認を求める**
3. `.env` から認証情報を読み込む（Bash ツールで `echo $SITE_XXX_USERNAME` 等）

> **重要:** `tos_status: restricted` のサイトは利用規約で自動アクセスが制限されている可能性があります。
> 実行する場合はユーザーの明示的な承認が必要です。自社管理サイトや明示的に許可されたサイトでの利用を推奨します。

### Step 1: ログイン

Playwright MCP ツールを使用してログインする:

```
1. browser_navigate → サイト設定の login_url にアクセス
2. browser_snapshot → ページ構造を確認し、ログインフォームを特定
3. browser_fill → username_field にユーザーID を入力
4. browser_fill → password_field にパスワードを入力
5. browser_click → login_button をクリック
6. browser_snapshot → ログイン成功を確認（ダッシュボード等が表示されるか）
```

**ログイン失敗時:**
- スクリーンショットを取得して原因を記録
- CAPTCHA がある場合はユーザーに手動対応を依頼
- 2段階認証がある場合はユーザーにコード入力を依頼

### Step 2A: データ取得（ブラウザ自動操作）

サイト設定の `target_pages` に従ってデータを収集する:

```
1. browser_navigate → 対象ページURL にアクセス
2. browser_wait → コンテンツの読み込み完了を待機（必要に応じて）
3. browser_snapshot → ページ内容を取得
4. 必要に応じて:
   - browser_click → ページネーション、「もっと見る」ボタン等を操作
   - browser_snapshot → 追加コンテンツを取得
   - 繰り返し（設定の max_pages まで）
```

**レート制限ルール（必須）:**
- ページ遷移間は **最低3秒** 待機する
- 連続リクエストは **10回ごとに10秒** の休憩を入れる
- サーバーエラー（5xx）を受けた場合は即座に停止しユーザーに報告

### Step 2B: データ取得（API経由 — api_available の場合）

サイト設定に `api_endpoint` がある場合、WebFetch ツールでAPIからデータを取得する:

```
1. WebFetch → api_endpoint にリクエスト（認証ヘッダー付き）
2. レスポンスをパース
3. ページネーションがある場合は次ページも取得
```

### Step 3: データ構造化

取得した生データを以下の共通フォーマットに構造化する:

```json
{
  "source_site": "サイト名",
  "collected_at": "2026-04-02T10:00:00+09:00",
  "category": "求人|不動産|市場データ|その他",
  "items": [
    {
      "title": "項目タイトル",
      "company_name": "企業名（該当する場合）",
      "details": {
        "フィールド名": "値"
      },
      "source_url": "元ページのURL",
      "raw_text": "加工前のテキスト"
    }
  ],
  "total_items": 10,
  "extraction_notes": "抽出時の注意点や除外した情報"
}
```

**個人情報の取り扱い:**
- 個人の氏名・電話番号・メールアドレスは原則として **マスキング** する
- 企業名・公開求人情報等の業務情報はそのまま保持
- 個人情報を保持する必要がある場合はユーザーに確認を取る

### Step 4: Notion データベースに保存

Notion MCP ツールを使用して「収集データ」データベースに保存する:

1. `notion-search` で「収集データ」データベースを検索
2. 各 item について:
   - `notion-search` で既存データとの重複をチェック（タイトル + ソースサイト で検索）
   - 重複なし → `notion-create-pages` で新規ページを作成
   - 重複あり → `notion-update-page` で既存ページを更新（必要に応じて）

**Notion ページのプロパティマッピング:**

| サイト設定 | Notion プロパティ | 値 |
|-----------|------------------|-----|
| - | タイトル (title) | item.title |
| site_name | ソースサイト (select) | サイト設定の site_name |
| category | カテゴリ (select) | 構造化時に判定 |
| - | 収集日時 (date) | collected_at |
| - | ステータス (status) | "未処理" |
| - | 企業名 (rich_text) | item.company_name |
| - | 詳細 (rich_text) | item.details をテキスト化 |
| - | 元URL (url) | item.source_url |
| - | 生データ (rich_text) | item.raw_text |

### Step 5: 結果の出力

収集結果のサマリを `/agents/web_scraper/output.json` に保存する:

```json
{
  "execution_summary": {
    "site": "サイト名",
    "executed_at": "2026-04-02T10:30:00+09:00",
    "method": "browser|api",
    "total_collected": 25,
    "new_items": 20,
    "updated_items": 3,
    "duplicates_skipped": 2,
    "errors": []
  },
  "items": [
    {
      "title": "項目タイトル",
      "notion_page_id": "xxx-xxx-xxx",
      "status": "created|updated|skipped"
    }
  ]
}
```

## 使用するツール

### Playwright MCP（ブラウザ自動操作）
- `browser_navigate`: URL遷移
- `browser_click`: 要素クリック
- `browser_fill`: フォーム入力
- `browser_snapshot`: ページ内容取得
- `browser_take_screenshot`: スクリーンショット
- `browser_wait`: 要素待機

### Notion MCP（データ保存）
- `notion-search`: データベース・ページ検索
- `notion-create-pages`: 新規ページ作成
- `notion-update-page`: ページ更新
- `notion-create-database`: データベース作成（初回セットアップ時）

### その他
- `Read`: サイト設定ファイルの読み込み
- `Write`: output.json への書き出し
- `Bash`: 環境変数の読み取り
- `WebFetch`: API経由でのデータ取得

## 法的コンプライアンス強化

### 個人情報保護法（2022年改正対応）
```
収集前の確認事項:
  - [ ] 収集するデータに個人情報（氏名・住所・電話番号・メールアドレス等）が含まれるか
  - [ ] 含まれる場合、利用目的は明確で適法か
  - [ ] 第三者提供に該当しないか（該当する場合は本人同意が必要）
  - [ ] 要配慮個人情報（人種・信条・病歴等）を含まないか

データ取り扱いルール:
  - 個人情報は原則としてマスキング（氏名→イニシャル、電話番号→下4桁のみ等）
  - 業務上必要な場合のみ Legal Agent の承認を得て保持
  - 保持する場合は暗号化（AES-256以上）必須
  - 保持期間は目的達成に必要な最短期間とし、期間経過後は速やかに削除
  - 漏洩時は72時間以内に個人情報保護委員会に報告（Legal Agent連携）
```

### 不正アクセス禁止法
```
遵守事項:
  - アクセス制限がかかっているページへの不正なアクセス試行は禁止
  - ログイン情報は正当に取得したもの（自社アカウント・許諾済みアカウント）のみ使用
  - 他人のID/パスワードの不正取得・使用は絶対禁止
  - セキュリティホールを利用したアクセスは禁止
  - 対象サイトのアクセス制御機能を回避する行為は禁止

判断基準:
  - 自社が管理するサイト → 問題なし
  - 業務委託先が許諾したサイト → 許諾範囲内で実行
  - 公開情報のみのサイト → robots.txt / 利用規約を確認
  - 会員制サイト → 自社アカウントかつ利用規約で自動アクセスが禁止されていないこと
```

### 著作権法
```
チェック項目:
  - [ ] 収集するコンテンツの著作権者は誰か
  - [ ] 「情報解析の用に供する場合」（著作権法30条の4）に該当するか
  - [ ] 収集データをそのまま公開・再配布しないか
  - [ ] データベースの著作物（著作権法12条の2）に該当しないか

安全な利用パターン:
  ○ 求人情報の構造化（事実データの抽出）
  ○ 価格比較のための数値データ収集
  ○ 市場調査のための統計的利用
  × 記事本文のコピー・転載
  × 画像・イラストの無断保存・利用
  × データベース全体の複製
```

### コンプライアンスチェック実行タイミング
```
毎回のスクレイピング実行前に以下を確認:
  1. robots.txt の確認 → 対象パスが Disallow されていないこと
  2. 利用規約の確認 → 自動アクセス・スクレイピングが禁止されていないこと
  3. サイト設定の tos_status を最新に更新
  4. Legal Agent に不明点があれば事前確認

判定結果を output.json の compliance_check フィールドに記録する
```

## データ品質検証

### 完全性チェック（Completeness）
```
検証項目:
  - 必須フィールドの充填率（目標: 95%以上）
  - 欠損値のパターン分析（特定フィールドに偏りがないか）
  - ページネーションの最終ページまで取得できているか
  - 取得件数と対象サイトの表示件数に乖離がないか

実装:
  total_expected = 対象サイト上の表示件数（可能な場合に取得）
  total_collected = 実際に収集した件数
  completeness_rate = total_collected / total_expected
  目標: completeness_rate >= 0.95
```

### 正確性チェック（Accuracy）
```
検証項目:
  - 数値データの範囲チェック（価格が負数でないか、日付が未来すぎないか等）
  - テキストデータの文字化け検出（UTF-8エンコーディング確認）
  - HTMLタグの残留（構造化時にタグが除去されているか）
  - フィールド間の整合性（開始日 < 終了日、住所と郵便番号の整合等）

実装:
  各アイテムに accuracy_score（0-100）を付与
  accuracy_score < 70 のアイテムは要手動確認としてフラグ付け
```

### 鮮度チェック（Freshness）
```
検証項目:
  - 対象サイトの最終更新日時と収集日時の差分
  - 前回収集データとの差分検出（変更があったアイテムの割合）
  - データの有効期限チェック（求人の掲載期限切れ等）

鮮度基準:
  - リアルタイム性が必要なデータ（価格・在庫）: 24時間以内
  - 定期更新データ（求人・物件）: 7日以内
  - 静的データ（企業情報）: 30日以内
  - 期限切れデータは expired フラグを付与し、Notionのステータスを更新
```

### 品質レポート
各収集実行の output.json に以下の品質メトリクスを追加:
```json
{
  "data_quality": {
    "completeness_rate": 0.98,
    "accuracy_score_avg": 92,
    "freshness_check": "passed",
    "duplicate_rate": 0.02,
    "total_flagged_items": 3,
    "quality_grade": "A"
  }
}
```

## アンチボット対策の倫理ガイド

### 許容される対応
```
○ 適切なUser-Agent文字列の設定（ボット名を明示）
○ robots.txt のクロール遅延指示（Crawl-delay）の遵守
○ リクエスト間隔を人間の閲覧速度に近づける（3秒以上の間隔）
○ サイトの負荷を考慮した時間帯指定（深夜帯に実行等）
○ エラーレスポンスを受けた際の即時停止
○ サイト管理者への事前連絡（可能な場合）
```

### 禁止される対応
```
× User-Agentの偽装（ブラウザと同一のUA文字列に偽装）
× IPアドレスのローテーション（プロキシプールの使用）
× CAPTCHA自動突破ツールの使用
× レート制限の意図的な回避
× JavaScriptによるフィンガープリンティング回避
× ヘッドレスブラウザ検出の回避（navigator.webdriverの上書き等）
× Cloudflare / Akamai 等のWAF/CDNセキュリティの迂回

例外:
  自社管理サイト → 上記制限は適用外（ただしサーバー負荷に配慮）
  クライアントから明示的な書面許諾がある場合 → Legal Agent確認の上で許容範囲内で実施
```

## スクレイピング効率化

### インクリメンタルクローリング
```
前回収集時点からの差分のみを取得する:
  1. 前回の output.json から最終収集日時を読み込む
  2. 対象サイトに「新着順」「更新日順」のソートがある場合はそれを利用
  3. 前回取得済みのアイテム（URLまたはIDで判定）に到達したら収集を停止
  4. 差分アイテムのみを Notion に追加/更新

効果: 実行時間とサーバー負荷を80-90%削減（2回目以降）
```

### 変更検出（Change Detection）
```
既存データの変更を効率的に検出する:
  1. 各アイテムの content_hash（本文のSHA-256ハッシュ）を保持
  2. 再取得時に content_hash を比較し、変更があったアイテムのみ更新
  3. HTTP の Last-Modified / ETag ヘッダーを活用（API経由の場合）
  4. 変更履歴を change_log として記録

content_hash の計算対象:
  - タイトル + 主要テキストフィールド（HTMLタグ除去後）
  - 価格・日付等の数値フィールド
  - 画像URLは除外（CDN URLの変動を無視するため）
```

### 重複排除（Deduplication）
```
重複判定基準（優先順位順）:
  1. 一意ID（対象サイトのアイテムID）→ 完全一致で重複判定
  2. URL → 正規化（クエリパラメータ除去・末尾スラッシュ統一）後に比較
  3. タイトル + ソースサイト → 類似度80%以上で重複候補

重複発見時の処理:
  - 同一ソースの重複 → 新しい方を保持、古い方を削除
  - 異なるソースの重複 → 両方保持し、cross_reference フラグを付与
  - Notion 側の重複 → マージ提案を output.json に記録（自動マージはしない）
```

## 障害復旧手順

### よくある障害パターンと復旧手順

| 障害パターン | 検知方法 | 復旧手順 |
|------------|---------|---------|
| ログインフォーム変更 | browser_snapshot でフォーム要素が見つからない | 1. スクリーンショット取得 2. 新しいセレクタを特定 3. サイト設定ファイルを更新 |
| ページ構造変更 | 期待するデータフィールドが取得できない | 1. 変更箇所を特定 2. データ抽出ロジックを調整 3. テスト実行で確認 |
| CAPTCHA表示 | ログイン後にCAPTCHAページが検出される | 1. 実行を一時停止 2. ユーザーに手動対応を依頼 3. CAPTCHA解決後に再開 |
| IP一時ブロック | 403/429レスポンスが連続する | 1. 即時停止 2. 最低1時間待機 3. リクエスト間隔を倍に延長して再試行 |
| セッションタイムアウト | 取得途中でログアウト状態になる | 1. ログイン状態を検出するチェックポイントを追加 2. タイムアウト検知時に再ログイン 3. 未完了分から再開 |
| Notion API制限 | Notion MCP がエラーを返す | 1. ローカル output.json にバックアップ保存 2. 5分待機後にリトライ 3. 3回失敗で中断し、後続バッチで投入 |
| 文字化け | 取得テキストに化けた文字が含まれる | 1. ページのエンコーディングを確認 2. UTF-8への変換を明示的に実施 3. 変換不能文字は置換文字で代替 |

### チェックポイント・リジューム
```
長時間の収集作業における中断・再開の仕組み:
  1. 10アイテムごとにチェックポイントを output.json に書き出す
  2. 障害発生時、最後のチェックポイントから再開する
  3. チェックポイントに含める情報:
     - 最後に成功したページURL
     - 処理済みアイテム数
     - 最後に処理したアイテムのID
     - タイムスタンプ
  4. 全アイテム処理完了後にチェックポイントファイルをクリーンアップ

チェックポイントファイル: /agents/web_scraper/checkpoint_{site_name}.json
```

## エラーハンドリング

| エラー | 対応 |
|--------|------|
| ログイン失敗 | スクリーンショットを取得し、ユーザーに報告。ID/PASS の確認を依頼 |
| CAPTCHA 表示 | ユーザーに手動でCAPTCHA解決を依頼 |
| 2段階認証 | ユーザーにコード入力を依頼 |
| ページ構造変更 | snapshot を確認し、セレクタを更新。ユーザーに設定ファイル更新を提案 |
| レート制限 (429) | 即座に停止し、待機時間後に再試行 |
| サーバーエラー (5xx) | 停止してユーザーに報告 |
| Notion 保存失敗 | エラー内容を記録し、ローカル output.json にバックアップ保存 |

## 実行例

```
/agents/web_scraper/prompt.md の手順に従って、
サイト設定「example_site.json」から情報を収集し、
Notionの「収集データ」データベースに保存してください。
```
