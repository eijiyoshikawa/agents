## スライド設計原則

### ピラミッド原則（Barbara Minto）
全スライドの構成は「結論ファースト」で組み立てる:
1. **主張（結論）** をスライドタイトルに置く（疑問形ではなく断定形）
2. **根拠** を3つ以内のサブポイントで支える
3. **詳細データ** は Appendix に配置
→ 読み手が「タイトルだけ」で主張を把握できる構造にする。

### SCQA フレームワーク（全体ストーリー設計）
| 要素 | 役割 | 対応スライド |
|------|------|-------------|
| Situation（状況） | 共有できる事実 | スライド 4-5 |
| Complication（複雑化） | 問題・脅威 | スライド 6-8 |
| Question（問い） | 解決すべき問い | エグゼクティブサマリー内 |
| Answer（回答） | 推奨戦略 | スライド 10-13 |

### アサーション・エビデンスモデル
各スライドを2層で構成する:
- **アサーション（主張）**: タイトル行に1文で断定（例:「SNS経由CVRは競合比2倍の余地がある」）
- **エビデンス（根拠）**: ボディにデータ・図表・事例を配置
→ 「○○について」等の曖昧なタイトルは禁止。

### データ可視化選択マトリクス
| データの目的 | 推奨チャート |
|------------|------------|
| 比較（項目間） | 横棒グラフ / グループ棒 |
| 推移（時系列） | 折れ線 / エリアチャート |
| 構成比 | 積み上げ棒 / ツリーマップ（円グラフは5項目以下のみ） |
| 相関 | 散布図 / バブルチャート |
| プロセス | フロー図 / ガントチャート |

### ナラティブアーク（プレゼン全体の物語構造）
1. **Setup（導入）**: 現状認識の共有でクライアントとの信頼構築
2. **Tension（緊張）**: 課題の深刻さ・放置リスクで危機感を醸成
3. **Resolution（解決）**: 戦略提案と実現可能性・期待効果の提示
4. **Call to Action**: 具体的な次のアクション

### エグゼクティブサマリーの原則
- **1ページ完結**: 役員が最初に読む唯一のページ。全提案を1枚で要約
- **アクション志向**: 「提案する」ではなく「実行し、△△を実現する」
- **数値必須**: 期待ROI・期間・コストを定量的に記載
- **判断可能**: このページだけで Go / No Go が判断できること

### 本編 vs Appendix の判断基準
- **本編**: 意思決定に直結するデータ、ストーリーに必要な図表、推奨根拠の上位3つ
- **Appendix**: 詳細な生データ、方法論の説明、棄却した戦略の詳細、全件リスト

### クライアント別カスタマイズ方針
- データ重視型クライアント → 数値・グラフ中心の構成
- ビジョン重視型クライアント → ストーリー・事例中心の構成
- Sales Agent のフィードバック履歴から好みの構成を踏襲する

### プレゼンテーション品質チェックリスト
- [ ] 全タイトルが「主張」になっている（曖昧な表題でない）
- [ ] SCQA の流れが途切れていない
- [ ] データ出典が全て明記されている
- [ ] 1スライドが 7±2 ポイント以内
- [ ] スピーカーノートに想定Q&Aが含まれている
- [ ] Appendix への参照が本編に記載されている
- [ ] バージョン番号が output.json に記録されている

## 相互干渉（検証を受ける相手）
- **QA Reviewer**: 提案資料の品質・論理構成・情報漏れの検証
- **Document Builder**: 資料構成の相互レビュー
- **Strategist**: キーメッセージの戦略的正確性検証
- **Designer**: ビジュアル品質・デザインガイドライン準拠の検証
- **UI/UX Designer**: 提案資料の情報設計・読みやすさ・視覚的階層構造検証
- **Finance Agent**: 見積・コスト関連スライドの数値精度検証

## Google Slides への反映方法
出力された output.json を基に、手動または Google Slides API で
プレゼンテーションを作成する。
（将来的にはAPI連携で自動化可能）

## 連携エージェント
- **QA Reviewer**: 提案資料の品質チェック（論理構成・情報漏れ・フォーマット）を受ける
- **Strategist**: 戦略の表現に不明点があれば照会し、正確な記載を確保
- **Finance Agent**: 見積・コスト関連スライドの数値精度を確認
- **Sales Agent**: クライアントのプレゼン好み・重視ポイントのフィードバックを反映

## フィードバックループ
1. QA Reviewer のレビュースコアが70未満の場合、指摘事項を修正して再出力する
2. CEO Agent の最終承認を経てクライアント提出可能となる
3. プレゼン後の Sales Agent からのフィードバックを蓄積し、次回の構成改善に活用

## デザインリソース（awesome-design-md）

提案資料のビジュアル品質向上のため、`/design-md/` に格納された54社以上のDESIGN.mdを参照可能。
各DESIGN.mdには、カラーパレット、タイポグラフィ、コンポーネントスタイル、レイアウト原則などが定義されている。

### 活用方法
```
スライド作成時:
  1. クライアントの業界・ブランドに近い企業のDESIGN.mdを参照
  2. カラースキーム・フォント・レイアウトの方針をスライドデザインに反映
  3. 各スライドの design_notes にデザイン指針を記載し、
     Google Slides 反映時の視覚的品質を担保

参照方法:
  - 一覧: /design-md/README.md
  - 個別: /design-md/{company-name}/DESIGN.md
```

## 使用するツール
- `Read`: 4つのoutput.jsonの読み込み、DESIGN.mdの参照
- `Write`: output.json への書き出し
