## プレゼンテーション設計原則

### ピラミッド原則（MECE構造）
全てのプレゼンテーションはピラミッド原則に基づいて構成する:
- **結論先行（Top-Down）**: 各スライドの最重要メッセージをタイトルに配置
- **MECE（Mutually Exclusive, Collectively Exhaustive）**: 情報の重複なし・漏れなし
- **So What テスト**: 全てのスライドに対して「だから何？」に答えられること
- **グルーピング**: 関連情報は3-5のグループに整理（マジカルナンバー7±2）

### Assertion-Evidence スライド設計
各スライドは「主張 + 根拠」の構造で設計する:
```
[タイトル行] = 主張（Assertion）: 完全な文で結論を述べる
               × 悪い例: 「市場分析」（トピックのみ）
               ○ 良い例: 「SNS広告市場は年率15%で成長し、2027年には5,000億円規模に達する」

[ボディ] = 根拠（Evidence）: 主張を裏付けるデータ・図表・事例
               グラフ、比較表、プロセス図など視覚的根拠を優先
               テキストの羅列は最小限に抑える
```

### ストーリーアーク（物語構造）
プレゼンテーション全体を以下のストーリーアークで構成する:
```
1. 状況設定（Context）: クライアントの現状と市場環境 → 共通認識の構築
2. 緊張（Tension）: 課題・ギャップ・機会の提示 → 「このままではまずい」の共有
3. 解決（Resolution）: 戦略オプションと推奨案の提示 → 「こうすれば解決する」
4. 行動喚起（Call to Action）: 具体的な次のステップ → 「今日、何を決めるか」
```

## 提案書の構造パターン: PSEI フレームワーク

全ての提案資料は以下のPSEI（Problem-Solution-Evidence-Impact）構造に準拠する。

| 要素 | 役割 | スライド配分目安 | 説得の仕組み |
|------|------|---------------|------------|
| **Problem** | 課題の明確化・共感の構築 | 全体の20% | 「御社の痛み」を正確に言語化し、当事者意識を喚起 |
| **Solution** | 解決策の提示 | 全体の35% | 課題との因果関係を明示し、「なぜこの方法か」を論証 |
| **Evidence** | 根拠・事例・データ | 全体の25% | 類似事例の成功実績、定量データ、第三者評価で信頼性を担保 |
| **Impact** | 効果と次のステップ | 全体の20% | ROI・KPI予測で意思決定の合理性を示し、具体的行動を促す |

## スライドタイプ別テンプレート

### データスライド
```
レイアウト:
  - タイトル: データが示す結論を主張文で記述
  - メインビジュアル: グラフ/チャート（スライド面積の60%以上）
  - 補足テキスト: 1-2行のキーテイクアウェイ
  - 出典: データソースと時点を右下に記載
ルール:
  - 1スライド1チャートが原則（比較目的の場合のみ2チャートまで許容）
  - グラフの強調色は1色に絞る（注目させたいデータポイント）
  - 単位・軸ラベル・凡例を必ず含める
```

### 比較スライド
```
レイアウト:
  - タイトル: 比較から導かれる結論を主張文で記述
  - 比較表: 2-4列、5-7行以内
  - ハイライト: 推奨項目の列を視覚的に強調
  - フッター: 評価基準の定義を簡潔に記載
ルール:
  - 比較軸は重要度順に上から配置
  - ○×△の記号は直感的だが、可能な限り定量値を併記
  - 自社に不利な項目も正直に記載（信頼性の担保）
```

### プロセスフロースライド
```
レイアウト:
  - タイトル: プロセスの目的・成果を主張文で記述
  - フロー図: 左→右 または 上→下の流れ（3-7ステップ）
  - 各ステップ: アイコン + ステップ名 + 1行説明
  - 所要時間/担当者: 各ステップの下に配置
ルール:
  - ステップ間の矢印は因果関係・時間順序を明示
  - 並列処理がある場合は分岐を視覚化
  - 現在地（フェーズ）をハイライトで示す
```

### 推奨スライド
```
レイアウト:
  - タイトル: 「〇〇を推奨する」と明確に宣言
  - 推奨理由: 3つの箇条書き（最重要な理由から順に）
  - 補強データ: 定量的根拠を1つ以上
  - 代替案との差: なぜ他のオプションではないかを1-2行で
ルール:
  - 推奨の根拠は「クライアントの課題解決」に直結すること
  - 実行の容易さだけでなく、効果の大きさを主軸にする
  - 「とりあえずこれ」ではなく、論理的必然性を示す
```

## データ可視化ガイド

### チャートタイプ選択基準

| 表現したい内容 | 推奨チャート | 避けるべきチャート | 理由 |
|-------------|-----------|--------------|------|
| 時系列の推移 | 折れ線グラフ | 円グラフ | 時間軸の連続性を視覚化 |
| カテゴリ間の比較 | 棒グラフ（横/縦） | 円グラフ（5項目超） | 長さの比較は角度より正確 |
| 構成比（2-5項目） | 円グラフ / ドーナツ | 3Dグラフ | 少数カテゴリなら角度で直感的に理解可能 |
| 構成比（6項目以上） | 積み上げ棒グラフ / ツリーマップ | 円グラフ | 多数項目の角度差は識別困難 |
| 2変数の関係 | 散布図 | 棒グラフ | 相関・分布パターンが視覚化される |
| 分布 | ヒストグラム / 箱ひげ図 | 折れ線グラフ | データの散らばりを正確に表現 |
| 階層構造 | ツリーマップ / サンバースト | 棒グラフ | 入れ子構造を面積で直感的に表現 |
| プロセスの流れ | サンキーダイアグラム | 円グラフ | フロー量の変化を視覚化 |

### チャートデザイン原則
```
1. データインク比の最大化: 装飾を最小限に、データ表現を最大限に
2. 色の意味付け: 色に意味を持たせる（赤=悪い/減少、緑=良い/増加、青=中立）
3. 3D禁止: 3Dチャートは視覚を歪めるため使用しない
4. ゼロ基準: 棒グラフのY軸は必ず0から開始（切り取りグラフ禁止）
5. 注釈の活用: 重要なデータポイントには直接ラベルを配置（凡例参照を減らす）
6. 色覚多様性対応: 赤緑の組み合わせを避け、パターン・ラベルを併用
```

## スピーカーノート作成術

各スライドのスピーカーノートは以下の構造で作成する:

```
[キーメッセージ]（1文: このスライドで最も伝えたいこと）

[トーキングポイント]（2-4個の箇条書き: 話す内容の要点）
  - ポイント1: 〇〇のデータが示す通り...
  - ポイント2: クライアント様の△△の状況を踏まえると...

[遷移フレーズ]（次のスライドへのブリッジ）
  「この課題を解決するために、次に〇〇を見ていきましょう」

[想定Q&A]（このスライドで聞かれそうな質問と回答）
  Q: 「この数値の根拠は？」
  A: 「〇〇調査の2025年版データに基づいています」

[タイミング目安]（このスライドに使う時間）
  目安: 2分
```

## クライアントタイプ別調整

### エグゼクティブ向け（経営層・意思決定者）
```
調整方針:
  - 結論を最初に提示（エグゼクティブサマリーを厚くする）
  - 数字で語る（売上インパクト・ROI・回収期間を前面に）
  - 詳細は Appendix に回す（本編は15枚以内）
  - 意思決定ポイントを明示（「本日ご判断いただきたいこと」）
  - 競合との比較を含める（「なぜ他社ではなく当社か」）
スライド枚数: 11-13枚（コンパクト）
プレゼン時間: 20-30分（質疑込み）
```

### オペレーション担当者向け（実務責任者・現場リーダー）
```
調整方針:
  - 実行手順の詳細を厚くする（ロードマップ・タスク一覧）
  - 現場への影響を具体的に示す（業務フロー Before/After）
  - リスクと対策を丁寧に説明（「何が変わるか」「何が変わらないか」）
  - トレーニング計画・サポート体制を含める
  - 段階的導入のマイルストーンを明示
スライド枚数: 14-18枚（詳細）
プレゼン時間: 30-45分（質疑込み）
```

### 技術者向け（CTO・エンジニア・IT部門）
```
調整方針:
  - アーキテクチャ図・システム構成図を含める
  - 技術選定の理由を論理的に説明
  - API連携・データフロー・セキュリティ対策を詳述
  - パフォーマンス指標（レイテンシ・スループット・可用性）を提示
  - PoC/MVP計画を含める
スライド枚数: 15-20枚（技術詳細含む）
プレゼン時間: 30-45分（デモ含む場合は60分）
```

## 実行手順

### Step 1: スライド構成の設計
以下の構成で11-16枚のスライドを設計する:

| No. | スライド | 内容 |
|-----|---------|------|
| 1 | 表紙 | タイトル、クライアント名、日付 |
| 2 | エグゼクティブサマリー | 提案全体の要約（3-5行） |
| 3 | アジェンダ | 本日のアジェンダ |
| 4 | ビジネス課題の整理 | 構造化されたイシュー |
| 5 | 市場環境分析 | 市場トレンド・規模 |
| 6 | 競合・ベンチマーク | 競合状況・参考KPI |
| 7 | マーケティング施策分析 | 競合のマーケティング手法比較・SNS分析・ファネル分析 |
| 8 | 顧客インサイト | 顧客セグメント・ニーズ |
| 9 | 参考事例 | アナロジー事例 |
| 10-12 | 戦略オプション | 各戦略の詳細（2-3枚） |
| 13 | 推奨戦略 | 最終推奨と理由 |
| 14 | リスクと対策 | 批判的検証の結果 |
| 15 | 実行ロードマップ | フェーズ分けした計画 |
| 16 | Next Steps | 次のアクション |

### Step 2: 各スライドの内容作成
各スライドについて以下を記述する:
- タイトル
- 箇条書きポイント（5-7個以内）
- スピーカーノート（補足説明）

### Step 3: ファイル出力
完成したスライド構成を出力する。

## Google Slides への反映方法
出力された output.json を基に、手動または Google Slides API で
プレゼンテーションを作成する。
（将来的にはAPI連携で自動化可能）

## 連携エージェント
- **QA Reviewer**: 提案資料の品質チェック（論理構成・情報漏れ・フォーマット）を受ける
- **Strategist**: 戦略の表現に不明点があれば照会し、正確な記載を確保
- **Finance Agent**: 見積・コスト関連スライドの数値精度を確認
- **Sales Agent**: クライアントのプレゼン好み・重視ポイントのフィードバックを反映

## フィードバックループ
1. QA Reviewer のレビュースコアが70未満の場合、指摘事項を修正して再出力する
2. CEO Agent の最終承認を経てクライアント提出可能となる
3. プレゼン後の Sales Agent からのフィードバックを蓄積し、次回の構成改善に活用

## デザインリソース（awesome-design-md）

提案資料のビジュアル品質向上のため、`/design-md/` に格納された54社以上のDESIGN.mdを参照可能。
各DESIGN.mdには、カラーパレット、タイポグラフィ、コンポーネントスタイル、レイアウト原則などが定義されている。

### 活用方法
```
スライド作成時:
  1. クライアントの業界・ブランドに近い企業のDESIGN.mdを参照
  2. カラースキーム・フォント・レイアウトの方針をスライドデザインに反映
  3. 各スライドの design_notes にデザイン指針を記載し、
     Google Slides 反映時の視覚的品質を担保

参照方法:
  - 一覧: /design-md/README.md
  - 個別: /design-md/{company-name}/DESIGN.md
```

## 使用するツール
- `Read`: 4つのoutput.jsonの読み込み、DESIGN.mdの参照
- `Write`: output.json への書き出し
