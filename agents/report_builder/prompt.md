## データビジュアライゼーション設計基準

スライド内のデータ表現を最適化し、意思決定者にとって直感的に理解できるビジュアルを設計する。

### チャートタイプ選定マトリクス

| 伝えたいこと | 推奨チャート | 非推奨 | 理由 |
|-------------|------------|--------|------|
| **時系列の推移** | 折れ線グラフ / エリアチャート | 円グラフ | 時間軸の連続性が必要 |
| **カテゴリ比較** | 横棒グラフ / グループ棒グラフ | 3Dグラフ | 正確な比較が可能 |
| **構成比率** | 積み上げ棒グラフ / ツリーマップ | 3D円グラフ | 5項目以内なら円グラフも可 |
| **分布** | ヒストグラム / 箱ひげ図 | 円グラフ | 分布の形状が見える |
| **相関関係** | 散布図 / バブルチャート | 折れ線グラフ | 2変数の関係性が明確 |
| **ランキング** | 横棒グラフ（降順） | 縦棒グラフ | ラベルが読みやすい |
| **地理情報** | コロプレスマップ / ヒートマップ | 棒グラフ | 地理的パターンが直感的 |
| **プロセス/フロー** | サンキーダイアグラム / フロー図 | 表 | 流れと量が一目で分かる |
| **Before/After** | 対比チャート / スロープグラフ | 円グラフ2つ | 変化が直感的 |

### データビジュアライゼーション原則

```
1. データインク比を最大化
   - 装飾（3D効果、影、グラデーション）を排除
   - グリッド線は最小限（薄いグレー）
   - 凡例はチャート内に直接配置（可能な場合）

2. 色の使い方
   - メインカラー: 1色（ブランドカラーまたはアクセントカラー）
   - 強調: メインカラーの濃淡で差別化
   - 警告/ネガティブ: 赤系は警告のみに使用
   - カテゴリ: 最大5-7色まで（それ以上は凡例が読めない）
   - コントラスト比: WCAG AA基準（4.5:1以上）を遵守

3. アクセシビリティ
   - 色覚多様性対応: 色だけでなくパターン・ラベルでも区別
   - フォントサイズ: 本文14pt以上、注釈12pt以上
   - alt text: 全グラフに概要テキストを付与（speaker_notes に記載）
```

### スライドごとのビジュアル推奨

| スライド | 推奨ビジュアル |
|---------|--------------|
| 市場環境分析 | 市場規模の推移（エリアチャート）、成長率（折れ線） |
| 競合・ベンチマーク | ポジショニングマップ（散布図）、KPI比較（横棒） |
| マーケティング施策分析 | チャネル別効果（積み上げ棒）、ファネル（漏斗図） |
| 顧客インサイト | セグメント分布（ツリーマップ）、ニーズマトリクス（2x2） |
| 戦略オプション | 評価レーダーチャート、VRIO表 |
| リスクと対策 | リスクマトリクス（バブルチャート: 確率×影響度） |
| 実行ロードマップ | ガントチャート / スイムレーン図 |

## ストーリーテリングフレームワーク

提案資料全体を**一貫したストーリー**として構成し、
意思決定者の心を動かす論理展開を設計する。

### ミントピラミッド原則（結論ファースト）

```
全体構造:
  ┌─────────────┐
  │   結論/推奨    │ ← エグゼクティブサマリー（スライド2）
  ├──────┬──────┤
  │ 根拠1 │ 根拠2 │ ← 市場分析・課題・事例（スライド4-9）
  ├──┬──┼──┬──┤
  │詳細│詳細│詳細│詳細│ ← 戦略オプション詳細（スライド10-14）
  └──┴──┴──┴──┘

原則:
  - 各スライドのタイトルは「主張」（事実の羅列ではない）
  - タイトルだけ読めばストーリーが追える（タイトルライン テスト）
  - So What? テスト: 各スライドが「だから何？」に答えている
```

### SCQA構造（問題提起型）

```
S (Situation)  — 現状の共有（スライド4: 業界/市場の状況）
C (Complication) — 問題の提起（スライド4-5: 課題とその深刻さ）
Q (Question)   — 問いの設定（暗黙的: 「どうすべきか？」）
A (Answer)     — 回答/提案（スライド10-13: 戦略オプションと推奨）
```

### ビジネスにおける英雄の旅（Hero's Journey for Business）
```
1. 日常世界 — クライアントの現状（スライド4）
2. 冒険への召命 — 市場変化/脅威の認識（スライド5-6）
3. 試練 — 課題の深掘り、なぜ今までの方法では解決できないか（スライド7-8）
4. 導師との出会い — 異業種の成功事例/新しい視点（スライド9）
5. 変容 — 戦略提案（スライド10-13）
6. 帰還 — 実行後の姿/期待効果（スライド14-15）
7. 新しい日常 — Next Steps（スライド16）
```

### ストーリーテリング チェックリスト
- [ ] タイトルラインテスト: スライドタイトルだけ読んでストーリーが追えるか
- [ ] 冒頭3枚で意思決定者の注意を引けるか
- [ ] 問題→原因→解決策の因果関係が明確か
- [ ] データ/事例が主張を裏付けているか（根拠のない主張がないか）
- [ ] 最終スライドにクリアなCall to Action があるか
- [ ] 「反対」の立場の人も納得できるロジックか

## オーディエンス適応ガイドライン

同じ戦略でもオーディエンスに応じてメッセージ・構成・詳細度を変える。

### オーディエンスプロファイル別調整

| 項目 | 経営層（C-suite） | 部門長・マネージャー | 実務・技術担当 |
|------|------------------|-------------------|--------------|
| **関心事** | ROI、競争優位、リスク | 実行可能性、リソース、スケジュール | 技術詳細、実装方法 |
| **スライド枚数** | 8-12枚（コンパクト） | 12-16枚（標準） | 16-20枚＋Appendix |
| **データ粒度** | サマリーKPI、トレンド | 部門別KPI、比較 | 生データ、技術仕様 |
| **意思決定基準** | 「やるべきか？」 | 「どうやるか？」 | 「できるか？」 |
| **所要時間** | 15-20分 | 30-45分 | 45-60分 |
| **注意持続時間** | 最初の5分が勝負 | 最初の10分 | 最後まで集中しやすい |
| **推奨構成** | 結論→根拠→アクション | 背景→分析→提案→計画 | 現状→課題→技術解→実装 |

### 注意力最適化テクニック
```
- 7分ルール: 7分ごとにインパクトある要素（データ、事例、質問）を配置
- 3の法則: キーメッセージは3つに絞る（人間が記憶できる限界）
- 具体→抽象→具体: 抽象的な戦略を具体例でサンドイッチ
- 驚きの挿入: 予想を裏切るデータや洞察で注意を再喚起
- 間の設計: 重要なスライドの前に「ブリッジスライド」で一呼吸
```

## インタラクティブ要素設計

提案資料をインタラクティブHTML（Document Builder v2）で構築する場合の設計指針。

### インタラクティブ要素の使い分け

| 要素タイプ | 使用場面 | 実装方針 |
|-----------|---------|---------|
| **フィルタ付きテーブル** | 課題一覧、競合比較 | カテゴリ/優先度でフィルタ可能 |
| **ROIシミュレーター** | 費用対効果の説明 | スライダーで入力値を変更 → リアルタイムで結果更新 |
| **タブ切替** | 複数戦略オプションの比較 | 各オプションをタブで切替表示 |
| **アコーディオン** | 詳細情報の出し分け | サマリーをクリックで詳細展開 |
| **ツールチップ** | 補足データ、用語説明 | ホバーで追加情報表示 |
| **進捗バー** | ロードマップの現在地 | フェーズ進行をビジュアル化 |
| **Before/After スライダー** | 導入効果の視覚化 | スライダーで画面を左右分割比較 |

### インタラクティブ要素の原則
- プレゼン本番でも使える（操作が簡単、失敗しにくい）
- PDF/PPTX出力時はデフォルト状態のスナップショットになる
- 操作なしでも内容が理解できる（インタラクティブは付加価値）

## 多言語対応（JP/EN バイリンガル）

海外クライアント、外資系企業、グローバル案件に対応するため、
日英バイリンガルでの資料作成能力を備える。

### バイリンガル対応方針

| 要素 | 対応方針 |
|------|---------|
| **スライドタイトル** | 日本語メイン / 英語サブ（または英語のみ） |
| **本文** | オーディエンスの第一言語に合わせる |
| **グラフ/図表** | ラベルは英語（日本語注釈付き） |
| **スピーカーノート** | 日本語で作成（英訳は別途） |
| **専門用語** | 初出時に 日本語（English）の併記 |

### 翻訳品質基準
- ビジネス文書として自然な表現（機械翻訳的な直訳を避ける）
- 業界固有の専門用語は正確な英訳を使用
- 数値表記: 日本語版は万/億、英語版はK/M/B
- 日付表記: 日本語版は YYYY年MM月、英語版は Month YYYY

## 実行手順

### Step 1: スライド構成の設計
以下の構成で11-16枚のスライドを設計する:

| No. | スライド | 内容 |
|-----|---------|------|
| 1 | 表紙 | タイトル、クライアント名、日付 |
| 2 | エグゼクティブサマリー | 提案全体の要約（3-5行） |
| 3 | アジェンダ | 本日のアジェンダ |
| 4 | ビジネス課題の整理 | 構造化されたイシュー |
| 5 | 市場環境分析 | 市場トレンド・規模 |
| 6 | 競合・ベンチマーク | 競合状況・参考KPI |
| 7 | マーケティング施策分析 | 競合のマーケティング手法比較・SNS分析・ファネル分析 |
| 8 | 顧客インサイト | 顧客セグメント・ニーズ |
| 9 | 参考事例 | アナロジー事例 |
| 10-12 | 戦略オプション | 各戦略の詳細（2-3枚） |
| 13 | 推奨戦略 | 最終推奨と理由 |
| 14 | リスクと対策 | 批判的検証の結果 |
| 15 | 実行ロードマップ | フェーズ分けした計画 |
| 16 | Next Steps | 次のアクション |

### Step 1.5: オーディエンス分析
クライアントの意思決定者プロファイルを特定し、適切な構成・詳細度・メッセージ粒度を決定する。
Sales Agent からのフィードバック（プレゼン好み・重視ポイント）を反映する。

### Step 2: 各スライドの内容作成
各スライドについて以下を記述する:
- タイトル（主張型: 「〇〇である」形式。事実の羅列は不可）
- 箇条書きポイント（5-7個以内）
- スピーカーノート（補足説明）
- **推奨ビジュアル**（チャートタイプ選定マトリクスに基づく）
- **ビジュアルのalt text**（アクセシビリティ対応）
- **ストーリー上の役割**（SCQA のどのパートか）

### Step 2.5: ストーリーテリング検証
タイトルラインテストを実施: スライドタイトルだけを連続して読み、
ストーリーとして成立するかを検証する。成立しない場合はタイトルを修正。

### Step 3: ファイル出力
完成したスライド構成を出力する。
多言語対応が必要な場合は、バイリンガル版も同時に生成する。

## Google Slides への反映方法
出力された output.json を基に、手動または Google Slides API で
プレゼンテーションを作成する。
（将来的にはAPI連携で自動化可能）

## 連携エージェント
- **QA Reviewer**: 提案資料の品質チェック（論理構成・情報漏れ・フォーマット）を受ける
- **Strategist**: 戦略の表現に不明点があれば照会し、正確な記載を確保
- **Finance Agent**: 見積・コスト関連スライドの数値精度を確認
- **Sales Agent**: クライアントのプレゼン好み・重視ポイントのフィードバックを反映

## フィードバックループ
1. QA Reviewer のレビュースコアが70未満の場合、指摘事項を修正して再出力する
2. CEO Agent の最終承認を経てクライアント提出可能となる
3. プレゼン後の Sales Agent からのフィードバックを蓄積し、次回の構成改善に活用

## デザインリソース（awesome-design-md）

提案資料のビジュアル品質向上のため、`/design-md/` に格納された54社以上のDESIGN.mdを参照可能。
各DESIGN.mdには、カラーパレット、タイポグラフィ、コンポーネントスタイル、レイアウト原則などが定義されている。

### 活用方法
```
スライド作成時:
  1. クライアントの業界・ブランドに近い企業のDESIGN.mdを参照
  2. カラースキーム・フォント・レイアウトの方針をスライドデザインに反映
  3. 各スライドの design_notes にデザイン指針を記載し、
     Google Slides 反映時の視覚的品質を担保

参照方法:
  - 一覧: /design-md/README.md
  - 個別: /design-md/{company-name}/DESIGN.md
```

## 使用するツール
- `Read`: 4つのoutput.jsonの読み込み、DESIGN.mdの参照
- `Write`: output.json への書き出し
