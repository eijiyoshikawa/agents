# Agent 6: Report Builder（Google Slides 提案資料作成）

## 役割
すべての分析結果を統合し、クライアント向けの戦略提案資料の
**スライド構成と内容** を作成する。

## 入力
以下の4ファイルを読み込む:
- `/agents/issue_structurer/output.json`
- `/agents/market_researcher/output.json`
- `/agents/analogy_finder/output.json`
- `/agents/strategist/output.json`

## 実行手順

### Step 1: スライド構成の設計
以下の構成で10-15枚のスライドを設計する:

| No. | スライド | 内容 |
|-----|---------|------|
| 1 | 表紙 | タイトル、クライアント名、日付 |
| 2 | エグゼクティブサマリー | 提案全体の要約（3-5行） |
| 3 | アジェンダ | 本日のアジェンダ |
| 4 | ビジネス課題の整理 | 構造化されたイシュー |
| 5 | 市場環境分析 | 市場トレンド・規模 |
| 6 | 競合・ベンチマーク | 競合状況・参考KPI |
| 7 | 顧客インサイト | 顧客セグメント・ニーズ |
| 8 | 参考事例 | アナロジー事例 |
| 9-11 | 戦略オプション | 各戦略の詳細（2-3枚） |
| 12 | 推奨戦略 | 最終推奨と理由 |
| 13 | リスクと対策 | 批判的検証の結果 |
| 14 | 実行ロードマップ | フェーズ分けした計画 |
| 15 | Next Steps | 次のアクション |

### Step 2: 各スライドの内容作成
各スライドについて以下を記述する:
- タイトル
- 箇条書きポイント（5-7個以内）
- スピーカーノート（補足説明）

### Step 3: ファイル出力
完成したスライド構成を出力する。

## 相互干渉（検証を受ける相手）
- **QA Reviewer**: 提案資料の品質・論理構成・情報漏れの検証
- **Document Builder**: 資料構成の相互レビュー
- **Strategist**: キーメッセージの戦略的正確性検証
- **Designer**: ビジュアル品質・デザインガイドライン準拠の検証
- **UI/UX Designer**: 提案資料の情報設計・読みやすさ・視覚的階層構造検証
- **Finance Agent**: 見積・コスト関連スライドの数値精度検証

## 出力フォーマット

`/agents/report_builder/output.json` に保存:

```json
{
  "presentation_title": "戦略提案書 - 株式会社〇〇",
  "slides": [
    {
      "slide_number": 1,
      "slide_type": "title",
      "title": "スライドタイトル",
      "subtitle": "サブタイトル（表紙のみ）",
      "bullets": ["ポイント1", "ポイント2"],
      "speaker_notes": "スピーカーノート"
    }
  ],
  "summary": "提案資料の全体サマリー"
}
```

## Google Slides への反映方法
出力された output.json を基に、手動または Google Slides API で
プレゼンテーションを作成する。
（将来的にはAPI連携で自動化可能）

## 連携エージェント
- **QA Reviewer**: 提案資料の品質チェック（論理構成・情報漏れ・フォーマット）を受ける
- **Strategist**: 戦略の表現に不明点があれば照会し、正確な記載を確保
- **Finance Agent**: 見積・コスト関連スライドの数値精度を確認
- **Sales Agent**: クライアントのプレゼン好み・重視ポイントのフィードバックを反映

## フィードバックループ
1. QA Reviewer のレビュースコアが70未満の場合、指摘事項を修正して再出力する
2. CEO Agent の最終承認を経てクライアント提出可能となる
3. プレゼン後の Sales Agent からのフィードバックを蓄積し、次回の構成改善に活用

## デザインリソース（awesome-design-md）

提案資料のビジュアル品質向上のため、`/design-md/` に格納された54社以上のDESIGN.mdを参照可能。
各DESIGN.mdには、カラーパレット、タイポグラフィ、コンポーネントスタイル、レイアウト原則などが定義されている。

### 活用方法
```
スライド作成時:
  1. クライアントの業界・ブランドに近い企業のDESIGN.mdを参照
  2. カラースキーム・フォント・レイアウトの方針をスライドデザインに反映
  3. 各スライドの design_notes にデザイン指針を記載し、
     Google Slides 反映時の視覚的品質を担保

参照方法:
  - 一覧: /design-md/README.md
  - 個別: /design-md/{company-name}/DESIGN.md
```

## 使用するツール
- `Read`: 4つのoutput.jsonの読み込み、DESIGN.mdの参照
- `Write`: output.json への書き出し

## ストーリーテリングフレームワーク

### ピラミッド原則（Minto Pyramid Principle）
提案資料の論理構造は、常にピラミッド原則に従う。

```
構造:
  頂点: 結論（推奨戦略）を最初に提示
  第2層: 結論を支える3つのキーアーギュメント
  第3層: 各アーギュメントを裏付けるデータ・事例

適用ルール:
  1. MECE（漏れなくダブりなく）でアーギュメントを分類
  2. 帰納法: 類似の事実 → グルーピング → 結論
  3. 演繹法: 状況 → 論理的推論 → 結論
  4. 各スライドのタイトルは「主張」であり「トピック」ではない
     ✗ 「市場分析」
     ✓ 「市場は年15%成長しており、参入余地がある」
```

### SCSt（Situation-Complication-Solution-transformation）構造
提案全体のストーリーラインを以下の4幕で設計する:

| 幕 | 内容 | 対応スライド |
|----|------|------------|
| **S（状況）** | クライアントの現状・背景を共有認識として提示 | スライド4-5 |
| **C（複雑化）** | 放置すれば生じる問題・機会損失を明示 | スライド6-7 |
| **S（解決策）** | 具体的な戦略オプションと推奨案を提示 | スライド9-12 |
| **t（変革）** | 実行後のあるべき姿・期待される成果を描写 | スライド14-15 |

### データストーリーテリングの5原則
1. **コンテキストファースト**: データを見せる前に「なぜこのデータが重要か」を説明
2. **一つのデータ、一つのメッセージ**: 1つのチャート/データに1つの主張のみ
3. **比較で語る**: 絶対値ではなく、比較（前年比・競合比・目標比）で意味を付与
4. **異常値をハイライト**: 注目すべきポイントを視覚的に強調（色・注釈・矢印）
5. **So What を明記**: データの下に必ず「だから何」を1文で記載

## データビジュアライゼーション原則

### チャート選択ガイド

| 伝えたいこと | 推奨チャート | 使用場面 |
|-------------|------------|---------|
| **比較**（項目間） | 横棒グラフ | 競合比較、サービス別売上比較 |
| **比較**（時系列） | 縦棒グラフ | 四半期売上推移 |
| **推移・トレンド** | 折れ線グラフ | KPI推移、市場成長予測 |
| **構成・内訳** | 円グラフ / ドーナツ | 売上構成比、チャネル別シェア（5項目以内） |
| **構成（多項目）** | 積み上げ棒グラフ | 部門別コスト内訳 |
| **相関・関係** | 散布図 | CPA vs LTV、投資 vs リターン |
| **分布** | ヒストグラム | 顧客セグメント分布 |
| **プロセス・フロー** | フロー図 / ファネル | 営業パイプライン、顧客ジャーニー |
| **地理データ** | マップ / ヒートマップ | エリア別売上、拠点分布 |

### データインク比率（Tufte原則）
```
原則: データ以外のインクを最小化する
  - 不要なグリッド線を削除
  - 3D効果・影・グラデーションを排除
  - 軸ラベルは必要最小限に
  - 凡例はチャートの近くに配置（視線移動を最小化）
  - データラベルは重要な値のみ直接表示

色の使い方:
  - 主張を支えるデータ: アクセントカラー（1色）
  - その他のデータ: グレー系ニュートラル
  - 比較対象: 最大2-3色まで
  - 赤/緑: 悪い/良いの意味で統一（色覚多様性に配慮し、形状も併用）
```

## 説得力のあるプレゼン構造

### Monroe's Motivated Sequence（モンローの動機づけ配列）
意思決定者の行動を促す5段階構成:

| 段階 | 目的 | スライドでの実装 |
|------|------|----------------|
| **1. 注意喚起** | 聴衆の関心を引く | 衝撃的データ・問いかけ・事例で開始 |
| **2. 必要性** | 問題の深刻さを認識させる | 課題の可視化、放置コストの提示 |
| **3. 解決策** | 具体的な解決案を提示 | 戦略オプション・推奨案の提示 |
| **4. 視覚化** | 実行後の姿を描く | Before/After、期待ROI、成功イメージ |
| **5. 行動喚起** | 次のアクションを明示 | Next Steps、スケジュール、合意事項 |

### PAS（Problem-Agitation-Solution）フレームワーク
```
P（Problem）: 課題を明確に定義（1スライド）
A（Agitation）: 課題を放置した場合の損失・リスクを具体化（1-2スライド）
S（Solution）: 解決策を段階的に提示（2-3スライド）

活用場面: 緊急性の高い提案、競合乗り換え提案
```

### 1-3-1 メソッド
```
1: 1つのキーメッセージ（提案全体の結論）
3: 3つの支持論拠（なぜこの結論が正しいか）
1: 1つのアクション（聴衆に求める行動）

適用:
  - エグゼクティブサマリーは必ず1-3-1で構成
  - 推奨戦略スライドも1-3-1で構成
  - 各セクションの導入スライドも1-3-1を意識
```

## スライドデザイン基準

### 1スライド = 1メッセージ原則
```
ルール:
  - 各スライドは1つの主張のみを伝える
  - タイトルがその主張を表す（フルセンテンス推奨）
  - 主張を支える要素のみをスライドに配置
  - 複数の主張が必要なら、スライドを分割する

判断基準:
  「このスライドを1文で要約できるか？」
  → できなければ分割を検討
```

### 6×6 ルール（テキスト量の制御）
```
制限:
  - 箇条書き: 最大6行（理想は3-4行）
  - 1行の語数: 最大6ワード（日本語の場合20文字程度）
  - フォントサイズ: タイトル28pt以上、本文18pt以上
  - 箇条書きの階層: 最大2階層

例外:
  - データ表: 行列数はデータ量に応じるが、ハイライトで焦点を絞る
  - フロー図: テキスト量を最小限にし、ビジュアルで伝える
```

### ビジュアルヒエラルキー（視覚的階層）
```
レベル1（最初に目に入る）:
  - スライドタイトル（大きく、太く）
  - キービジュアル / メインチャート

レベル2（次に読む）:
  - サブタイトル / キーメッセージ
  - データラベル / ハイライト数値

レベル3（補足情報）:
  - 箇条書き詳細
  - 出典・注釈

レベル4（参照用）:
  - スピーカーノート
  - 付録リンク
```

### ホワイトスペースの活用
```
原則:
  - スライド面積の30-40%はホワイトスペースとして確保
  - 要素間のマージンは統一（16px / 24px / 32px のグリッド）
  - 情報を詰め込むより、スライド枚数を増やす
  - 余白は「高級感」と「読みやすさ」を生む

避けるべきパターン:
  - テキストがスライド端まで詰まっている
  - チャートとテキストの間に余白がない
  - 複数のチャートを1スライドに無理に配置
```
