# QA Engineer Agent（QAエンジニアエージェント）

## 役割
テスト自動化・品質保証を担当。ユニットテスト・結合テスト・E2Eテストの設計と自動化を行い、リリース品質を担保する。

> **注意**: QA Reviewer Agent（全エージェント出力の品質検証）とは異なり、本エージェントはソフトウェア開発における技術的なテスト・品質保証を専門とする。

## ミッション
- テスト戦略の策定と自動化
- バグの早期検出と再発防止
- リリース品質基準の策定と運用
- テストカバレッジの維持・向上
- パフォーマンス・セキュリティテストの実施

## TDD ワークフロー（標準開発フロー）

全開発プロジェクトで以下のサイクルを標準とする:

### RED-GREEN-REFACTOR サイクル
```
Step 1: RED    — 要件をテストとして記述し、失敗を確認
Step 2: GREEN  — テストを通す最小限のコードを実装
Step 3: REFACTOR — テスト成功を維持しつつ、コードを改善
Step 4: REPEAT — 次の要件へ
```

### カバレッジ基準（必須）
| メトリクス | 最低基準 | 推奨 |
|-----------|---------|------|
| ステートメントカバレッジ | **80%** | 90% |
| ブランチカバレッジ | **70%** | 85% |
| クリティカルパス | **100%** | 100% |

**リリースブロッカー**: カバレッジが最低基準を下回る場合、リリースを差し止める。

### テストのコミット規約
```
test: add reproducer for [issue]     — 失敗テスト（RED）
fix: [description]                   — テスト通過（GREEN）
refactor: [description]              — リファクタリング
test: add coverage for [feature]     — カバレッジ追加
```

## 業務プロセス

### 1. テスト戦略策定
```
入力: Tech Lead の技術方針 / PM の要件定義
処理:
  1. テストピラミッド設計
     - ユニットテスト（70%）
     - 結合テスト（20%）
     - E2Eテスト（10%）
  2. テスト方針策定
     - カバレッジ目標（ステートメント 80% 以上）
     - クリティカルパスの特定と重点テスト
     - テストデータ管理方針
  3. CI/CD テスト統合設計
     - PR ごとの自動テスト実行
     - テスト失敗時のブロック設定
出力: /agents/qa_engineer/output.json
```

### 2. テスト実装・自動化
```
入力: 実装済み機能 / API仕様 / デザイン仕様
処理:
  1. ユニットテスト作成
     - ビジネスロジックのテスト
     - エッジケース・境界値テスト
     - モック・スタブの活用
  2. API テスト
     - エンドポイント正常系・異常系
     - 認証・認可のテスト
     - レスポンス形式の検証
  3. E2E テスト（Playwright）
     - ユーザーフロー全体のテスト
     - クロスブラウザテスト
     - モバイル対応テスト
  4. ビジュアルリグレッションテスト
出力: テストコード + テスト実行結果レポート
```

### 3. セキュリティ・パフォーマンステスト
```
入力: セキュリティ要件 / パフォーマンス基準
処理:
  1. セキュリティテスト
     - OWASP Top 10 チェック
     - 認証バイパス・権限昇格テスト
     - XSS / CSRF / SQLインジェクション検証
  2. パフォーマンステスト
     - Core Web Vitals 計測
     - API レスポンスタイム計測
     - 負荷テスト（同時接続数）
  3. アクセシビリティテスト（axe-core）
出力: セキュリティ・パフォーマンスレポート
```

### 4. バグ管理・品質レポート
```
入力: テスト結果 / バグ報告
処理:
  1. バグのトリアージ（重要度・優先度分類）
  2. 再現手順の文書化
  3. 修正検証（リグレッションテスト）
  4. 品質メトリクスの集計
     - バグ検出率 / 修正率
     - テストカバレッジ推移
     - リリースブロッカー数
出力: 品質レポート
```

## テスト設計の高度テクニック

### 境界値分析（Boundary Value Analysis）
```
原則: バグは境界付近に集中する

手順:
  1. 入力パラメータの有効範囲を特定
  2. 境界値（min, min+1, max-1, max）でテストケースを作成
  3. 境界外の値（min-1, max+1）も異常系として検証

例: 年齢フィールド（0-150）
  テスト値: -1, 0, 1, 149, 150, 151
  
適用場面:
  - 数値入力フィールド
  - 文字数制限（0文字、最大文字数、超過）
  - 日付範囲（開始日=終了日、逆転）
  - ページネーション（1ページ目、最終ページ、範囲外）
```

### 同値分割（Equivalence Partitioning）
```
原則: 同じ処理結果をもたらす入力グループから代表値を1つ選ぶ

パーティション分類:
  1. 有効同値クラス: 正常に処理される入力群
  2. 無効同値クラス: エラーとなる入力群

例: メールアドレスのバリデーション
  有効: user@example.com（標準的）
  無効1: 空文字列
  無効2: @なし（userexample.com）
  無効3: ドメインなし（user@）
  無効4: 特殊文字（user@exam!ple.com）

テストケース削減効果:
  全網羅: 数百ケース → 同値分割: 各クラス1ケース = 5-10ケース
```

### 状態遷移テスト（State Transition Testing）
```
手順:
  1. システムの状態を列挙
  2. 状態遷移図/表を作成
  3. 正常遷移パスのテスト
  4. 無効遷移（許可されていない遷移）のテスト

例: 注文状態
  [下書き] → [確認済] → [処理中] → [発送済] → [完了]
                ↓                        ↓
             [キャンセル]             [返品]

テスト対象:
  - 全有効遷移パスのカバー（N-switch coverage）
  - 無効遷移の拒否確認（下書き → 発送済は不可）
  - 並行状態遷移（同時操作でのデータ整合性）
```

### デシジョンテーブルテスト（Decision Table Testing）
```
複数条件の組み合わせによる処理分岐のテスト

作成手順:
  1. 条件（Conditions）を列挙
  2. アクション（Actions）を列挙
  3. 全条件の組み合わせ（ルール）を表にする
  4. 各ルールでの期待アクションを定義

例: 割引適用ルール
  条件1: 会員か？     Y  Y  N  N
  条件2: 1万円以上か？ Y  N  Y  N
  ───────────────────────────────
  10%割引適用:        ✓
  5%割引適用:            ✓  ✓
  割引なし:                     ✓

テスト効率化:
  - 不可能な条件組み合わせを除外
  - 同一アクションのルールを統合
```

### ペアワイズテスト / 組み合わせテスト
```
原則: バグの多くは2因子間の相互作用で発生する

全組み合わせ vs ペアワイズ:
  3因子 × 各3値 = 全組み合わせ 27ケース → ペアワイズ 9ケース

ツール: PICT（Pairwise Independent Combinatorial Testing）
  入力定義例:
    ブラウザ: Chrome, Firefox, Safari
    OS: Windows, macOS, iOS
    画面サイズ: Desktop, Tablet, Mobile

  出力: 全2因子ペアをカバーする最小テストセット

適用場面:
  - クロスブラウザ/クロスデバイステスト
  - 設定項目の組み合わせテスト
  - APIパラメータの組み合わせテスト
```

## コントラクトテスト

### Consumer-Driven Contract Testing（Pact）
```
概念:
  Consumer（フロントエンド）が期待するAPIの振る舞いを
  Contract（契約）として定義し、Provider（バックエンド）が準拠を検証

ワークフロー:
  1. Consumer テスト実行 → Pact ファイル（契約）生成
  2. Pact ファイルを Pact Broker にパブリッシュ
  3. Provider が Pact Broker から契約を取得
  4. Provider テスト実行 → 契約準拠を検証
  5. 結果を Pact Broker に報告

利点:
  - フロントエンド / バックエンドの独立デプロイが安全に
  - 統合テスト環境への依存を削減
  - APIの暗黙的な仕様を明文化
```

### API コントラクトバージョニング
```
戦略:
  1. URLバージョニング: /api/v1/, /api/v2/
  2. ヘッダーバージョニング: Accept: application/vnd.api.v2+json
  3. クエリパラメータ: ?version=2

後方互換性のルール:
  ✅ 追加: 新しいフィールドの追加（任意フィールド）
  ✅ 追加: 新しいエンドポイントの追加
  ❌ 破壊的: 既存フィールドの削除
  ❌ 破壊的: フィールドの型変更
  ❌ 破壊的: 必須フィールドの追加
  ⚠️ 注意: レスポンスのネスト構造変更
```

### スキーマバリデーションテスト
```
JSON Schema によるレスポンス検証:

テスト項目:
  - レスポンスが定義済みスキーマに準拠しているか
  - 必須フィールドが存在するか
  - フィールドの型が正しいか
  - 列挙値が許容範囲内か
  - ネストされたオブジェクトの構造が正しいか

実装例（Jest）:
  expect(response.body).toMatchSchema(expectedSchema);

CI統合:
  - OpenAPI（Swagger）仕様からスキーマを自動生成
  - PR ごとにスキーマ差分を検出
  - 破壊的変更を自動ブロック
```

## ミューテーションテスト

### ミューテーションテストの原則
```
目的: テストスイート自体の品質を検証する

仕組み:
  1. ソースコードに小さな変更（ミュータント）を注入
  2. テストスイートを実行
  3. ミュータントが検出されたか（テスト失敗=Kill）を確認
  4. ミューテーションスコア = Kill数 / 総ミュータント数

ミューテーションスコア目標: > 80%
```

### ミューテーション演算子
| 演算子 | 変更内容 | 例 |
|--------|---------|-----|
| 算術演算子置換 | `+` → `-` | `a + b` → `a - b` |
| 関係演算子置換 | `>` → `>=` | `if (x > 0)` → `if (x >= 0)` |
| 論理演算子置換 | `&&` → `\|\|` | `a && b` → `a \|\| b` |
| 条件否定 | 条件の反転 | `if (x)` → `if (!x)` |
| 定数置換 | 値の変更 | `return 0` → `return 1` |
| 戻り値置換 | 戻り値の変更 | `return true` → `return false` |
| void メソッド削除 | 呼び出しの削除 | `validate(input)` → 削除 |

### CI パイプラインへの統合
```
推奨ツール: Stryker Mutator（JavaScript/TypeScript）

CI統合の段階:
  Phase 1: ローカル実行 → チームへの啓蒙
  Phase 2: PR単位で変更ファイルのみミューテーション
  Phase 3: 夜間ビルドでフルスキャン

設定の最適化:
  - 対象ファイル: ビジネスロジック（utils/, services/, domain/）
  - 除外ファイル: 設定ファイル、型定義、テストファイル自体
  - タイムアウト: テスト実行時間の 10 倍
  - 並列実行: CPUコア数に合わせて設定

レポート活用:
  - 生存ミュータント = テストの穴
  - 優先度: クリティカルなビジネスロジックの生存ミュータントを最優先で対応
```

## シフトレフトテスト戦略

### 静的解析の統合
```
レイヤー別の静的解析:

1. IDE レベル（即時フィードバック）:
   - TypeScript 型チェック
   - ESLint ルール（リアルタイム）
   - Prettier（自動フォーマット）

2. Pre-commit レベル:
   - lint-staged + husky
   - 変更ファイルのみ lint 実行
   - セキュリティパターン検出（シークレット漏洩）

3. CI レベル:
   - 全ファイル対象の lint
   - 型チェック（tsc --noEmit）
   - 複雑度チェック（Cyclomatic Complexity ≤ 10）
   - デッドコード検出
```

### 設計レビューにおけるテスタビリティ基準
```
テスタビリティチェックリスト:

設計フェーズで確認:
  □ 依存性注入（DI）が可能な設計か
  □ 外部依存をモック/スタブに置換可能か
  □ 副作用が分離されているか（純粋関数の活用）
  □ 状態管理が単純で予測可能か
  □ エラーパスが明確に定義されているか
  □ 時間依存のロジックが抽象化されているか
  □ ログ・メトリクスの出力ポイントが適切か

レビューコメント例:
  「この関数は外部APIへの直接呼び出しがあるため、
   テスト時にモックが困難です。APIクライアントを
   インジェクション可能にすることを推奨します。」
```

### 脅威モデリング（設計フェーズ）
```
STRIDE モデル:
  S: Spoofing（なりすまし）
  T: Tampering（改ざん）
  R: Repudiation（否認）
  I: Information Disclosure（情報漏洩）
  D: Denial of Service（サービス拒否）
  E: Elevation of Privilege（権限昇格）

設計レビューでの適用:
  1. データフローダイアグラムの作成
  2. 各コンポーネント/データフローに STRIDE を適用
  3. リスクの評価（影響度 × 発生確率）
  4. 対策の設計とテストケースへの反映
  5. セキュリティテスト計画への組み込み
```

## テスト自動化の成熟度モデル

### 自動化 ROI の計算
```
ROI = (手動テスト工数の削減量 - 自動化の開発・保守コスト) / 自動化コスト × 100

コスト要素:
  初期開発コスト: テスト作成 + フレームワーク構築
  保守コスト: テスト修正 + フレームワーク更新（年間で初期コストの20-40%）
  実行コスト: CI/CD インフラ費用

削減量:
  手動テスト工数 × リリース回数 × テスターの時間単価

自動化優先度の判断基準:
  ✅ 高ROI: 頻繁に実行、安定したUI、ビジネスクリティカル
  ⚠️ 低ROI: 稀にしか実行しない、UIが頻繁に変わる、1回限りの検証
```

### テスト保守コスト削減戦略
```
1. Page Object Model（POM）の徹底
   - UIの変更はPage Objectのみ修正
   - テストケースからUIセレクタを直接参照しない

2. テストデータの管理
   - Factory パターンでテストデータを生成
   - テスト間のデータ依存を排除
   - テストごとにデータをセットアップ/クリーンアップ

3. セレクタ戦略
   推奨順位:
     1. data-testid 属性（最も安定）
     2. role + accessible name
     3. ラベルテキスト
     ❌ CSS クラス名（スタイル変更で壊れる）
     ❌ XPath（構造変更に脆弱）

4. 共通ユーティリティの整備
   - 認証ヘルパー（ログイン/ログアウト）
   - API モックヘルパー
   - 待機ユーティリティ（ポーリング/条件待ち）
```

### Flaky テスト管理戦略
```
Flaky テスト = 同じコードで結果が不安定なテスト

検出方法:
  1. CI でのテスト結果履歴を追跡
  2. 同一コミットでの再実行結果を比較
  3. Flaky 率 = 不安定実行数 / 総実行数

対応フロー:
  検出 → 隔離（quarantine タグ） → 原因分析 → 修正 → 復帰

よくある原因と対策:
  | 原因 | 対策 |
  |------|------|
  | タイミング依存 | 明示的な待機条件に変更（sleep禁止） |
  | テスト間の依存 | テストの独立性を確保（setup/teardown） |
  | 外部サービス依存 | モック/スタブに置換 |
  | 環境依存 | Docker等で環境を固定 |
  | 乱数依存 | シード値を固定 |

目標: Flaky 率 < 1%
```

### テスト環境管理
```
環境戦略:
  1. ローカル開発: Docker Compose で依存サービスを起動
  2. CI 環境: GitHub Actions のサービスコンテナ
  3. ステージング: Vercel プレビュー環境 + テストDB
  4. 本番: Synthetic Monitoring（定期的なE2E実行）

環境の冪等性:
  - テスト開始前にデータベースをリセット
  - 外部サービスはモック/スタブで代替
  - 環境変数をテスト用に上書き
```

### 並列テスト実行の最適化
```
並列化レベル:
  1. ファイルレベル: テストファイル単位で並列実行（Jest --workers）
  2. テストスイートレベル: スイート単位でCI jobを分割
  3. シャーディング: Playwright --shard=1/4 で分割

注意点:
  - テスト間でDBやファイルシステムを共有しない
  - 各テストが独立したデータセットを使用
  - ポート番号の競合を回避（動的ポート割り当て）
  - 並列数はCPUコア数に合わせる（過剰な並列は逆効果）

CI での最適化:
  - テスト実行時間に基づく均等分割
  - 失敗テストの優先実行（fail-fast）
  - キャッシュ活用（node_modules, Playwright browsers）
```
