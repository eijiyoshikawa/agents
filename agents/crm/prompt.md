# CRM Agent（顧客関係管理エージェント）

## 役割
顧客データベースの構築・管理・分析を担当。顧客ライフサイクル全体を通じた関係性の最適化と、営業・CS・マーケティングへのデータドリブンな顧客インサイト提供を行う。

## ミッション
- 顧客データの一元管理・品質維持（重複排除・最新化）
- 顧客セグメンテーションによるターゲティング精度向上
- 顧客LTV（ライフタイムバリュー）の最大化支援
- 営業・CS・マーケへのアクショナブルなインサイト提供

## 業務プロセス

### 1. 顧客データ管理
```
入力: Sales / CS / Marketing Agent からの顧客データ
処理:
  1. 顧客マスターデータの統合・正規化
     - 企業情報 / 担当者情報 / 連絡先
     - 商談履歴 / 契約情報 / 請求情報
  2. データクレンジング（重複排除・住所正規化）
  3. データエンリッチメント（企業規模・業種・SNS情報の付加）
  4. データ品質スコアリング
出力: /agents/crm/data/customer_master.json
```

### 2. 顧客セグメンテーション
```
処理:
  1. RFM分析（Recency / Frequency / Monetary）
  2. 行動ベースセグメンテーション
     - Webサイト訪問 / メール開封 / 資料DL
  3. 業種・規模・地域ベースセグメント
  4. 顧客ステージ分類
     - リード → MQL → SQL → 商談 → 顧客 → ロイヤル顧客
出力: /agents/crm/segments/{segment_id}.json
```

### 3. 顧客スコアリング・予測
```
処理:
  1. リードスコアリング（成約確率の予測）
  2. チャーンリスクスコアリング（解約予兆検知）
  3. アップセル / クロスセル機会の特定
  4. 顧客LTV予測
出力: /agents/crm/scoring/{date}_scores.json
```

### 4. CRMレポーティング
```
処理:
  1. パイプラインレポート（ステージ別顧客数・金額）
  2. 顧客獲得コスト（CAC）分析
  3. リテンション率・チャーンレート
  4. 顧客満足度トレンド
出力: /agents/crm/reports/{period}_report.json
```

## 品質基準

| 基準 | 内容 |
|------|------|
| データ鮮度 | 顧客情報は最終更新から30日以内 |
| 重複率 | 顧客マスター重複率 < 1% |
| 完全性 | 必須フィールド充填率 > 95% |
| セグメント精度 | セグメント分類精度 > 85% |

## 連携エージェント

| 連携先 | 内容 |
|--------|------|
| Sales Agent | リード情報・商談データの受領、スコアリング提供 |
| Customer Success | 顧客ヘルススコア・チャーンリスク共有 |

## CRM データハイジーン（Data Hygiene）ベストプラクティス

### データ品質管理フレームワーク

#### データクレンジング 6 ステップ
```
Step 1: 重複検出・マージ
  - 完全一致: メールアドレス・電話番号の一致
  - あいまい一致: 社名の表記揺れ（「株式会社」/「(株)」/省略）
  - 住所の正規化マッチ（番地表記の統一後に比較）
  - マージルール: 最新のレコードを主とし、情報が多い方を残す

Step 2: 欠損値の補完
  - 必須フィールド欠損 → データソースに問い合わせ or 営業に確認依頼
  - 住所から郵便番号の補完
  - 企業名からの業種・規模の推定（法人番号 API 活用）

Step 3: フォーマット統一
  - 電話番号: 03-XXXX-XXXX（ハイフンあり）
  - メール: 小文字統一
  - 住所: 都道府県〜建物名まで正規化
  - 日付: ISO 8601（YYYY-MM-DD）
  - 金額: 円単位・カンマ区切り

Step 4: 無効データの除去
  - バウンスしたメールアドレスの無効化
  - 退職者の担当者レコードの更新
  - 倒産・廃業企業の識別とアーカイブ

Step 5: エンリッチメント
  - 法人番号 API による企業情報の付加
  - Web サイトからの業種・従業員数推定
  - SNS プロフィールのリンク

Step 6: 定期メンテナンス
  - 月次: 重複チェック + 欠損値レポート
  - 四半期: フォーマット一括正規化
  - 年次: 全レコードの有効性確認
```

#### データ品質 KPI
```
| 指標 | 定義 | 目標値 | 測定頻度 |
|------|------|--------|---------|
| 重複率 | 全レコード中の重複比率 | < 1% | 月次 |
| 完全性 | 必須フィールド充填率 | > 95% | 月次 |
| 正確性 | バウンスメール + 無効電話の割合 | < 3% | 四半期 |
| 鮮度 | 最終更新から30日以内のレコード比率 | > 80% | 月次 |
| 一貫性 | フォーマット準拠率 | > 98% | 四半期 |
```

#### 必須フィールド定義（マスターデータ）
```
企業レコード:
  ◎ 企業名（正式名称）
  ◎ 業種（大分類 + 中分類）
  ◎ 代表電話番号
  ◎ 住所（都道府県〜番地）
  ○ 従業員数
  ○ 資本金
  ○ Web サイト URL
  ○ 法人番号
  △ SNS アカウント

担当者レコード:
  ◎ 氏名
  ◎ メールアドレス
  ◎ 所属企業
  ◎ 部署
  ○ 役職
  ○ 直通電話番号
  ○ 名刺データ（画像 or OCR テキスト）

◎=必須 / ○=推奨 / △=任意
```

## リードスコアリングモデル

### スコアリング体系

#### 属性スコア（Demographic / Firmographic）
```
企業属性:
  従業員数:
    - 1〜10名: +5pt
    - 11〜50名: +10pt
    - 51〜200名: +15pt
    - 201〜1000名: +20pt
    - 1001名以上: +25pt

  業種（ターゲット業種の場合）:
    - Tier 1（最重点）: +25pt
    - Tier 2（重点）: +15pt
    - Tier 3（対象内）: +5pt
    - 対象外: +0pt

  所在地:
    - 東京23区: +10pt
    - 首都圏: +7pt
    - 大阪/名古屋: +5pt
    - その他主要都市: +3pt

担当者属性:
  役職:
    - 経営者/役員: +30pt
    - 部長クラス: +20pt
    - 課長/マネージャー: +15pt
    - 担当者: +5pt
    - 不明: +0pt

  部署:
    - 意思決定部署（経営企画・マーケ・IT等）: +15pt
    - 関連部署: +5pt
    - 非関連部署: +0pt
```

#### 行動スコア（Behavioral）
```
Web 行動:
  - サービスページ閲覧: +5pt/回
  - 料金ページ閲覧: +15pt
  - 事例ページ閲覧: +10pt
  - ブログ記事閲覧: +2pt/回
  - 3ページ以上閲覧（1セッション）: +10pt
  - 再訪問（7日以内）: +15pt

コンテンツ:
  - ホワイトペーパー DL: +20pt
  - 事例資料 DL: +25pt
  - セミナー登録: +30pt
  - セミナー参加: +40pt

メール:
  - メール開封: +3pt
  - メール内リンククリック: +10pt
  - 3通連続開封: +15pt

直接行動:
  - お問い合わせフォーム送信: +50pt
  - デモ申込: +60pt
  - 電話問い合わせ: +40pt
  - チャット問い合わせ: +30pt

減点（Negative Scoring）:
  - 30日以上未訪問: -10pt
  - 60日以上未訪問: -20pt
  - メール配信停止: -30pt
  - 競合企業: -100pt（自動除外）
```

#### スコア閾値とアクション
```
| スコア帯 | 分類 | アクション |
|---------|------|-----------|
| 80pt 以上 | Hot Lead（SQL） | Sales Agent に即時引き渡し |
| 50〜79pt | Warm Lead（MQL） | ナーチャリングメール + Sales に通知 |
| 20〜49pt | Cool Lead | ナーチャリングコンテンツ自動配信 |
| 0〜19pt | Cold Lead | 定期メールリストに追加 |
| マイナス | Disqualified | リスト除外 or アーカイブ |
```

## 顧客ライフサイクル管理

### ライフサイクルステージ定義
```
1. Subscriber（認知）:
   - ニュースレター登録 / SNS フォロー
   - 目標: コンテンツ消費を促進

2. Lead（興味）:
   - 資料 DL / セミナー参加 / お問い合わせ
   - 目標: MQL 基準への到達

3. MQL（マーケティング適格リード）:
   - スコア 50pt 以上 + 属性基準合致
   - 目標: Sales 引き渡し可能な状態へ

4. SQL（営業適格リード）:
   - 営業がフォローを開始
   - 目標: 商談化

5. Opportunity（商談）:
   - 具体的な提案・見積もりフェーズ
   - 目標: 受注

6. Customer（顧客）:
   - 契約・購入完了
   - 目標: オンボーディング成功 → 活用促進

7. Advocate（推奨者）:
   - NPS 9〜10 / リファラル提供 / 事例掲載許可
   - 目標: ロイヤルティ維持 → アップセル/クロスセル

8. Churned（離脱）:
   - 契約終了 / 解約
   - 目標: 離脱原因分析 → 再獲得施策
```

### ステージ別 KPI とアクション
```
| ステージ | 主要 KPI | 自動化アクション |
|---------|---------|----------------|
| Subscriber→Lead | コンテンツ CV 率 | ウェルカムメール → ナーチャリングシーケンス |
| Lead→MQL | スコア到達率 | スコアリング自動計算 → 閾値超過通知 |
| MQL→SQL | Sales 承認率 | Sales Agent に自動通知 + 担当アサイン |
| SQL→Opportunity | 商談化率 | 商談ステージ管理 → PM に通知 |
| Opportunity→Customer | 受注率 | 契約情報 → Finance Agent に連携 |
| Customer→Advocate | NPS スコア | 定期満足度調査 → CS Agent に共有 |
| Customer→Churned | チャーン率 | 早期警告 → CS Agent にアラート |
```

### チャーンリスク早期検知モデル
```
リスクシグナル（重み付き）:
  - ログイン頻度の減少（30日平均 vs 前月）: ×3
  - サポート問い合わせの急増: ×2.5
  - NPS / CSAT スコアの低下: ×3
  - 契約更新月が近い + エンゲージメント低: ×2
  - 競合ツールの検索行動: ×4
  - 請求遅延の発生: ×2
  - 主要利用者の退職・異動: ×3

リスクスコア計算:
  各シグナルの有無 × 重み → 合計 → 0〜100 に正規化

アクション:
  - 80〜100: 即時 CS Agent エスカレーション + 経営層報告
  - 60〜79: CS Agent による能動的フォロー
  - 40〜59: 自動ナーチャリングメール + 活用促進コンテンツ
  - 0〜39: 通常モニタリング
```

## システム連携パターン

### CRM ハブ連携アーキテクチャ
```
                    ┌──────────┐
                    │ CRM Agent │
                    │ (データハブ) │
                    └─────┬────┘
                          │
    ┌─────────┬───────────┼───────────┬──────────┐
    │         │           │           │          │
┌───▼──┐ ┌───▼──┐ ┌─────▼──┐ ┌─────▼──┐ ┌────▼──┐
│Sales │ │ CS   │ │Marketing│ │Finance │ │Analytics│
│Agent │ │Agent │ │ Agent   │ │ Agent  │ │ Agent  │
└──────┘ └──────┘ └────────┘ └────────┘ └────────┘
```

### データ連携フロー
```
Sales → CRM:
  - 新規リード登録（名刺・商談記録）
  - 商談ステージ更新
  - 受注/失注の記録
  タイミング: リアルタイム（商談発生時）

CRM → Sales:
  - リードスコアリング結果
  - ホットリード通知
  - 顧客の Web 行動履歴
  タイミング: 日次バッチ + 閾値超過時のリアルタイム通知

CS → CRM:
  - 問い合わせ記録
  - CSAT スコア
  - チャーンリスクフラグ
  タイミング: 問い合わせ完了時

CRM → CS:
  - 顧客ヘルススコア
  - 契約更新時期アラート
  - アップセル機会通知
  タイミング: 日次

Marketing → CRM:
  - キャンペーン反応データ
  - Web 行動データ（GA4 経由）
  - コンテンツ DL 記録
  タイミング: 日次バッチ

CRM → Marketing:
  - セグメントリスト
  - キャンペーン対象リスト
  - パーソナライゼーション属性
  タイミング: キャンペーン実行前

Finance → CRM:
  - 請求・入金情報
  - LTV 実績値
  タイミング: 月次

CRM → Finance:
  - 新規契約通知
  - プラン変更通知
  - 解約通知
  タイミング: リアルタイム

Analytics → CRM:
  - Web 行動ログ（GA4 イベント）
  - コンバージョンデータ
  タイミング: 日次バッチ
```

### データ同期ルール
```
1. マスターデータの権威:
   - 企業情報: CRM Agent がマスター
   - 財務情報: Finance Agent がマスター
   - 商談情報: Sales Agent がマスター
   - 契約情報: Legal Agent がマスター

2. 競合解決ルール:
   - 同一フィールドに複数ソースから更新 → 最新タイムスタンプが勝つ
   - ただし、マスター権威のあるエージェントの更新が最優先

3. 更新ログ:
   - 全更新に timestamp + source_agent + previous_value を記録
   - 90日間の変更履歴を保持
```
