# リスキリング助成金対応 LMS 設計書

> **対象助成金**: 人材開発支援助成金 **事業展開等リスキリング支援コース**
> **提供形態**: クライアント提供（SaaS / 受託）＝マルチテナント
> **本書の範囲**: 設計とコスト計算のみ（実装は別リポジトリ）
> **作成**: 開発部門（Tech Lead 統括） / **検証**: Devil's Advocate・Legal・Finance
> **最終更新**: 2026-07-15

## 0. 重要な前提と免責

- 本書の助成金要件は一般に公開されている制度概要に基づく**設計上の想定**であり、法的助言ではない。
- **実際の要件は年度の要領・様式・管轄労働局の運用で変わる。** 申請前に必ず **最新の支給要領・社会保険労務士・管轄労働局** に確認すること（この確認プロセス自体を製品の運用フローに組み込む）。
- 特に **e ラーニングの「修了確認」の証跡** は労働局審査で最も見られる論点であり、本設計の中核に据える。

## 1. 事業展開等リスキリング支援コースの要点（設計に効く部分）

| 項目 | 想定内容 | LMS への影響 |
|------|---------|------------|
| 訓練形態 | OFF-JT（e ラーニング・通信制を含む） | 動画視聴＝e ラーニングとして扱う |
| 賃金助成 | **e ラーニングは賃金助成の対象外**（受講時間の実地管理が困難なため）。経費助成が中心 | 「賃金助成のための厳密な時間打刻」よりも、**修了の確認**に証跡を寄せる |
| 訓練時間要件 | 実訓練時間の下限あり（例：10時間以上） | コース総尺・受講時間の集計が必須 |
| 修了確認 | 「訓練を修了したことが確認できる記録」が必要（受講履歴・視聴ログ・確認テスト・修了証 等） | **視聴ログ + 確認テスト + 修了証** の三点セットを標準装備 |
| 保存義務 | 関係書類は一定期間（原則 5 年）保存 | エクスポート & 改ざん耐性のあるログ保管が必要 |

> ⚠️ 数値（下限時間・助成率・限度額）は年度で変動する。LMS は**しきい値をテナント設定で可変**にし、要領改定にコード変更なしで追随できるようにする（後述 §5）。

### 労働局審査で「効く」証跡（本 LMS が生成するもの）
1. **受講者ごとの受講履歴** … 受講日時・教材名・視聴区間・累計受講時間
2. **視聴の実態証明** … 早送り／放置を排した「実視聴時間」
3. **修了の証明** … 確認テスト合格記録 + 修了証（受講者名・コース名・受講時間・修了日）
4. **改ざんされていないことの担保** … 追記専用ログ + ハッシュチェーン（§6）

## 2. スコープ

### MVP に含む
- マルチテナント（クライアント企業ごとにデータ分離）
- ロール：SaaS 運営 / テナント管理者（人事）/ 受講者
- コース・教材（動画）・受講者の管理
- 動画プレイヤー + **視聴イベントログ**（heartbeat・seek 検出）
- **実視聴時間の集計と修了判定エンジン**
- 確認テスト（修了確認用）
- 修了証 PDF 生成
- **助成金監査用エクスポート**（受講記録 CSV / PDF、期間・受講者・コース単位）
- 進捗ダッシュボード（テナント管理者向け）

### MVP に含めない（Phase 2 以降）
- SCORM / xAPI 完全準拠、外部 LMS 連携
- 顔認証・生体による本人確認（なりすまし対策は Phase 2、MVP は認証 + 操作ログで代替）
- 集合研修（OFF-JT 対面）の出欠管理
- 賃金助成向けの厳密労働時間連携（本コースの e ラーニングでは対象外のため優先度低）
- 多言語 UI、モバイルアプリ（レスポンシブ Web で対応）

## 3. システムアーキテクチャ

```
┌────────────────────────── クライアント（ブラウザ / レスポンシブ）──────────────────────────┐
│  受講者UI（視聴・テスト）      テナント管理UI（進捗・エクスポート）    運営UI（テナント管理）  │
└───────────────┬───────────────────────────┬───────────────────────────┬────────────────┘
                │  視聴イベント(数秒毎)         │  管理API                    │
        ┌───────▼───────────────────────────▼───────────────────────────▼───────┐
        │                    アプリケーション（Next.js App Router / API）           │
        │  Auth/RBAC │ テナント分離 │ 視聴ログ受信 │ 集計・修了判定 │ 監査エクスポート │
        └───────┬───────────────────────┬───────────────────────┬──────────────┘
                │                        │                        │
        ┌───────▼───────┐      ┌─────────▼─────────┐    ┌─────────▼─────────┐
        │  RDB(Postgres) │      │ 動画 R2 + CDN       │    │ オブジェクトストレージ │
        │ 受講者/コース/  │      │ 自前HLS/署名URL      │    │ 修了証PDF/エクスポート │
        │ 視聴ログ/結果   │      │ egress無料           │    │ (R2)                 │
        └───────────────┘      └─────────▲─────────┘    └───────────────────┘
                                          │ (アップロード時) ffmpeg エンコード → HLS/ABR
```

### 技術選定（社内標準準拠）
| レイヤ | 採用 | 理由 |
|-------|------|------|
| フロント | Next.js (App Router) + TypeScript + Tailwind | 社内標準・SEO/SSR・和文B2B は `feer` デザインベースライン |
| バックエンド | Next.js Route Handlers（or 独立 API）+ Prisma | 型安全・単一リポで完結 |
| DB | PostgreSQL（Supabase / Neon） | 行レベルセキュリティ(RLS)でテナント分離が堅牢 |
| 認証 | Auth.js / Supabase Auth（メール+パスワード, SSO 拡張可） | 監査ログと相性良 |
| 動画配信 | **Cloudflare R2 + CDN による自前HLS配信** | **egress（配信転送料）無料**で配信単価を最小化。署名URL・DL不可で著作権/漏洩配慮 |
| 動画エンコード | ffmpeg パイプライン（アップロード時に一度だけ HLS/ABR 化） | 実視聴に依存しない一度きりの処理。配信単価に効かない |
| 動画プレイヤー | hls.js（イベント発火）+ 配信抽象化層 | play/pause/seek/timeupdate/ended を捕捉。R2↔Stream/Mux を切替可能 |
| PDF | サーバサイド生成（例：`@react-pdf` 相当） | 修了証・監査帳票 |
| ホスティング | Vercel | 社内標準 |

> **なぜ Cloudflare R2 + 自前HLS か（配信単価の最小化）**: 従量配信SaaS（Cloudflare Stream / Mux）は「視聴分数 × 単価」で配信費が受講量に線形増加する。対して **R2 は egress（配信転送料）が無料**で、コストは「保管容量」と「リクエスト数」のみ。**視聴が増えても配信費がほぼ増えない**のが最大の利点。代償はアップロード時のエンコード（ffmpeg で HLS/ABR 化）と署名URLの内製で、これは**一度きりの処理**なので配信単価には効かない。視聴ログはプレイヤー側で取得するため、配信基盤を差し替えても集計ロジックは不変。
>
> **フォールバック**: 立ち上げ最速を優先するなら Cloudflare Stream / Mux（エンコード不要）でも動く。プレイヤーに配信抽象化層を挟み、後から R2 へ移行可能にしておく（§11 ロックイン対策）。コスト比較は COST_BASELINE.md §2/§5。

## 4. データモデル（中核）

```
Tenant(テナント=クライアント企業)
  id, name, subsidy_settings(JSON: 修了しきい値/下限時間等), created_at

User
  id, tenant_id, role(owner|admin|learner), email, name,
  employee_no(対象労働者の特定), auth_provider, created_at

Course
  id, tenant_id, title, description, category(事業展開分野),
  required_watch_ratio(既定0.95), pass_score(確認テスト), published_at

Lesson(教材=動画)
  id, course_id, title, video_asset_id(Stream/Mux), duration_sec, order

Enrollment(受講登録)
  id, tenant_id, user_id, course_id, status(active|completed|expired),
  enrolled_at, completed_at

── 視聴ログ（中核・追記専用）─────────────────────────────
WatchEvent           ← プレイヤーから数秒毎に届く生イベント
  id, enrollment_id, lesson_id, user_id,
  type(play|pause|seek|timeupdate|ended|heartbeat),
  position_sec, playback_rate, session_id,
  client_ts, server_ts,   ← 時刻はサーバ側を正とする

  id, enrollment_id, lesson_id, user_id,
  start_sec, end_sec, counted_sec   ← 重複排除済みの実視聴秒

LessonProgress(教材ごと集計)
  enrollment_id, lesson_id, covered_ratio, watched_sec,
  is_completed, first_watched_at, last_watched_at

── 修了確認 ──────────────────────────────────────────
QuizAttempt
  id, enrollment_id, lesson_id|course_id, score, passed, answered_at

Certificate(修了証)
  id, enrollment_id, cert_no, learner_name, course_title,
  total_watched_sec, completed_at, pdf_url, issued_at

── 監査 ────────────────────────────────────────────
AuditLog(操作証跡)
  id, tenant_id, actor_id, action, target, ip, ua, ts

```

**テナント分離**: 全テーブルに `tenant_id`。PostgreSQL の **Row Level Security** でクエリレベルに強制し、アプリのバグでも越境参照を防ぐ（受託 SaaS の必須要件）。

## 5. 視聴ログ & 修了判定エンジン（本 LMS の心臓部）

### 5.1 収集（クライアント → サーバ）
- プレイヤーが **5〜10 秒ごとに heartbeat**（現在位置・再生速度・session_id）を送信。
- `play/pause/seek/ended` は都度送信。**seek（早送り）は position の飛びで検出**。
- 時刻は **サーバ受信時刻 (`server_ts`) を正**とし、クライアント時計の改ざんに依存しない。
- 離席・タブ非アクティブは `visibilitychange` + heartbeat 欠落で検知し、その区間は実視聴に**加算しない**。

### 5.2 実視聴時間の再構成（不正加算を防ぐ）
```
生イベント列 → [session ごとに時系列ソート]
  → 連続する再生区間 [start_sec, end_sec] を抽出（heartbeat 間隔で連続とみなす）
  → 早送りでスキップした区間は含めない
  → 複数回視聴の重複区間はマージ（同じ所を2回見ても2倍に数えない）
  → counted_sec = 動画尺のうち「実際に一度以上再生された区間」の合計
```
- `covered_ratio = Σ(ユニーク視聴区間) / duration_sec`
- **完了条件（テナント設定で可変）**: `covered_ratio ≥ required_watch_ratio(既定0.95)` **かつ** 確認テスト合格 `passed=true`。
- 再生速度上限（例：2.0x まで）を設け、超過視聴は counted に含めないか警告。

### 5.3 なぜ「区間カバレッジ方式」か
- 「累計再生時間」だけだと、同じ 1 分を 10 回再生して 10 分と偽装できる。
- 「最終 position だけ」だと、末尾にシークするだけで完了扱いにできる。
- **ユニーク区間カバレッジ**なら「動画のどこを実際に見たか」を面で証明でき、労働局の「実際に受講したか」という問いに正面から答えられる。

### 5.4 しきい値の可変設計
要領改定・コース特性に対応するため、以下を **Tenant / Course 設定**に外出し（コード変更不要）：
- `required_watch_ratio`（完了とみなす視聴カバレッジ）
- コース `下限受講時間`（監査で「10時間以上」等を満たすか判定）
- 確認テスト `pass_score`
- 有効受講期間（開始〜終了）

## 6. 改ざん耐性・証跡の信頼性

助成金は「後から作った記録」を嫌う。証跡の信頼性を機械的に担保する：

1. **追記専用（append-only）**: `WatchEvent` は UPDATE/DELETE を DB 権限とアプリ双方で禁止。
2. **ハッシュチェーン**: 各イベントに `hash = H(prev_hash + payload)`。途中改変は連鎖が壊れて検出可能。
3. **サーバ時刻の権威化**: `server_ts` を正とし、必要に応じ日次で外部タイムスタンプ（TSA / ログの日次ハッシュ公開）を付与（Phase 2）。
4. **エクスポート時のハッシュ添付**: 監査帳票 PDF/CSV にファイルハッシュを記録（`ExportJob.hash`）し、提出物の同一性を後から検証可能に。
5. **操作証跡 `AuditLog`**: 管理者による受講データ変更を全記録（誰が・いつ・何を）。

## 7. 監査エクスポート（提出物の自動生成）

テナント管理者が期間・受講者・コースを指定して出力：

| 帳票 | 形式 | 内容 |
|------|------|------|
| 受講記録一覧 | CSV / PDF | 受講者×コース：受講開始/修了日、実視聴時間、カバレッジ、テスト結果 |
| 受講履歴明細 | CSV | 教材単位の視聴区間・視聴日時（証跡の裏付け） |
| 修了証 | PDF | 受講者名・コース名・受講時間・修了日・証明番号 |
| 実施結果サマリ | PDF | コース概要・対象者・総訓練時間（申請書添付を想定） |

- 出力は非同期ジョブ化（大量受講者対応）、生成物はハッシュ付きで保存。
- **申請様式そのものの自動生成は Phase 2**（様式が年度改定されるため、MVP は「必要データを網羅した汎用帳票」に留め、社労士が転記できる状態を作る）。

## 8. セキュリティ・コンプライアンス（社内 Security Standards 準拠）

- **テナント分離**: RLS + アプリ層ガードの二重化。
- **動画保護**: 署名付き短命 URL・ダウンロード不可・直リンク防止。著作権配慮（`asset_collector` 方針準拠）。
- **個人情報**: 従業員氏名・社員番号を扱う → 暗号化保存・アクセス最小権限・保持期間管理。
- **認証**: パスワードハッシュ、レート制限、（Phase 2で）MFA / SSO。
- **監査ログ**: 状態変更操作を全記録。
- **シークレット管理**: 環境変数 / シークレットマネージャ、`.env` は Git 管理外。
- コミット前チェック（シークレット・入力検証・XSS/CSRF・認可・レート制限）は社内基準に従う。

## 9. なりすまし対策（コスト×効果で段階導入）

| 手段 | 効果 | コスト | MVP |
|------|------|-------|-----|
| 認証 + セッション + 操作/IPログ | 基本の本人特定 | 低 | ✅ |
| 受講中の定期的な在席確認（クリック/軽問） | 放置・代理の抑止 | 低 | ✅（簡易版） |
| 確認テスト（修了要件） | 内容理解の証明 | 低 | ✅ |
| 顔写真キャプチャ / 顔認証 | 代理受講の強い否定 | 中〜高 | Phase 2 |

MVP は「認証 + 在席確認 + 確認テスト + 実視聴カバレッジ」で、代理・放置を実務上十分に抑止する設計とする。

## 11. Devil's Advocate（想定リスクと対策）

| リスク | 内容 | 対策 |
|-------|------|------|
| 要件の年度変動 | 助成率・下限時間・様式が改定される | しきい値を設定外出し / 様式自動生成は Phase 2 / 社労士確認を運用に組込 |
| 「ログ＝受講」の否認 | 労働局が視聴ログを実受講と認めない可能性 | 視聴ログ**単独に依存せず** 確認テスト・修了証・在席確認を束ねる |
| なりすまし | 代理受講の指摘 | 認証+在席確認、Phase 2 で顔認証 |
| 配信コスト超過 | （従量SaaS採用時のみ）視聴時間に比例して増える | **R2+自前HLS採用で egress無料化** → 視聴増でも配信費ほぼ横ばい |
| エンコード基盤の運用 | ffmpeg パイプライン・署名URL の内製が必要 | アップロード時の一度きり処理に限定。障害時もアップロードのみ再実行で復旧 |
| 個人情報事故 | 従業員データ漏洩 | RLS・暗号化・最小権限・監査ログ |
| ベンダーロックイン | 配信基盤依存 | プレイヤーに抽象化層を設け R2 ↔ Stream/Mux を切替可能に |
